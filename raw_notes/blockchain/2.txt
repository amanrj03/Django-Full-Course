# 1. First: What is a Distributed System?

Your PPT defines a distributed system as a computing paradigm where:

> **Two or more nodes work with each other in a coordinated fashion to achieve a common outcome.** 

### Simple meaning

Imagine 5 computers:

```text
       N1
      /  \
    N2 -- N3
     \    /
      N4
       |
      N5
```

Instead of one computer doing everything, multiple computers cooperate.

Each computer is called a **node**.

They communicate with each other and try to maintain a common result/state.

---

# 2. Centralized vs Distributed System

This distinction is extremely important.

### Centralized

```text
              SERVER
             /  |  \
            /   |   \
          N1    N2    N3
```

One central system controls the data/process.

If the central server fails, the system may be seriously affected.

### Distributed

```text
       N1 -------- N2
       | \         |
       |  \        |
       |   \       |
       N3 -------- N4
          \       /
             N5
```

Multiple nodes cooperate.

There isn't necessarily one single machine that performs all functions.

---

# 3. What is a Node?

A **node** is a participant/computer in a distributed network.

Your PPT notes that nodes have processing and memory resources and can behave as:

* Honest
* Faulty
* Malicious
* Byzantine



Don't confuse these.

### Honest node

Follows the protocol correctly.

### Faulty node

May malfunction because of hardware/software/network problems.

Example:

```text
Node crashes
```

### Malicious node

Intentionally attempts to violate the protocol or harm the system.

### Byzantine node

A node that can behave arbitrarily/unpredictably, potentially sending conflicting or irrational information to other nodes.

Your PPT specifically describes a Byzantine node as one that can perform irrational behavior. 

---

# 4. Why are Distributed Systems Difficult?

Suppose we have:

```text
N1 ↔ N2 ↔ N3 ↔ N4 ↔ N5
```

All nodes need to agree about something.

But what if:

* N4 is malicious?
* N2 crashes?
* Network connection between N2 and N3 breaks?
* Messages arrive late?
* Different nodes receive different information?

Then the nodes may have different views of reality.

Your PPT identifies two major challenges:

### 1. Coordination between nodes

Nodes must communicate and cooperate.

### 2. Fault tolerance

The system should continue functioning even when some components fail.

# 5. Byzantine Generals Problem ⭐⭐⭐⭐⭐

This is a **very important theory topic**.

You should absolutely prepare it for a 5-mark question and potentially a 10-mark question.

## The story

Imagine several generals surrounding an enemy city.

They need to decide:

> **Attack or Retreat?**

They can communicate with each other.

But some generals may be traitors.

The problem is:

```text
General A → ATTACK
General B → ATTACK
General C → RETREAT
General D → ATTACK
```

How can the honest generals reach the same decision when some participants may deliberately send false information?

That's the basic idea behind the:

> **Byzantine Generals Problem (BGP)**

---

# 6. Why is Byzantine Problem Important to Blockchain?

This is the connection you need to understand.

Blockchain has many nodes:

```text
N1   N2   N3   N4   N5   N6
 \    |    |    |    |   /
       Distributed Network
```

They don't necessarily trust each other.

Some nodes could:

* lie
* send incorrect information
* behave maliciously
* stop responding

Yet the network needs to maintain a **consistent ledger state**.

So blockchain needs mechanisms that allow honest nodes to agree despite potentially faulty/malicious nodes.

That brings us to **consensus**.

We'll study consensus properly in Module 3.

# 7. Network Partition

Your PPT gives an example:

> **N4 is a Byzantine node and L2 is a broken or slow network link.** 

A broken/slow link can cause a **network partition**.

Imagine:

```text
Group A                  Group B

N1 ---- N2        X       N3 ---- N4
                        

       broken link
```

The two sides may temporarily have different information.

Therefore:

```text
Network problem
      ↓
Nodes cannot communicate properly
      ↓
Different views of system state
      ↓
Consistency problem
```

This is one of the reasons distributed systems need fault-tolerance and consensus mechanisms.

# 8. PBFT

Your PPT mentions that the Byzantine Generals Problem was addressed by **Practical Byzantine Fault Tolerance (PBFT)**, presented by Castro and Liskov in 1999. 

For now, remember:

> **PBFT is a Byzantine fault-tolerant consensus algorithm designed to allow a distributed system to operate correctly even when some nodes behave maliciously.**

# 10. What is a Blockchain?

Your PPT's technical definition is:

> A blockchain is a **peer-to-peer, distributed ledger that is cryptographically secure, append-only, immutable, and updateable through consensus/agreement among peers.** 

This definition is **very important**.

Break it into 6 parts.

---

## A. Peer-to-Peer

Nodes communicate directly with other nodes.

There isn't necessarily a central server controlling every transaction.

---

## B. Distributed Ledger

A ledger is basically a record of transactions.

For example:

```text
Alice → Bob       ₹100
Bob → Charlie     ₹50
Charlie → David   ₹20
```

In a distributed ledger, copies/state of the ledger are maintained across participating nodes.

---

## C. Cryptographically Secure

Blockchain uses cryptographic mechanisms such as:

* Hash functions
* Digital signatures
* Public-key cryptography

Your architecture PPT specifically identifies public-key cryptography, digital signatures and cryptographic hash functions as important cryptographic components. 

---

## D. Append-only

New information is added rather than casually replacing old information.

Think:

```text
Block 1
   ↓
Block 2
   ↓
Block 3
   ↓
Block 4
```

---

## E. Immutable

Historical information is extremely difficult to alter without detection or without overcoming the network's security/consensus assumptions.

Why?

Because blocks are cryptographically connected.

We'll see this in detail in the cryptography module.

---

## F. Consensus-based

Nodes must follow the blockchain's consensus mechanism to determine the accepted state.

```text
Transaction
     ↓
Validation
     ↓
Consensus
     ↓
Accepted
     ↓
Blockchain
```

# 15. What is the Previous Block Hash?

Suppose:

```text
Block 1
Hash = ABC123
```

Then Block 2 contains:

```text
Previous Hash = ABC123
```

So:

```text
Block 1
Hash = ABC123
      ↓
Block 2
Previous Hash = ABC123
Hash = XYZ789
      ↓
Block 3
Previous Hash = XYZ789
```

This creates the chain.

This is why changing an old block affects the cryptographic links afterward.

Later, when we study **hash functions**, you'll understand exactly why.

---

# 16. What is a Merkle Root?

Suppose Block 1 contains four transactions:

```text
T1
T2
T3
T4
```

Hash each:

```text
H(T1) = H1
H(T2) = H2
H(T3) = H3
H(T4) = H4
```

Then combine them:

```text
H(H1 + H2) = H12
H(H3 + H4) = H34
```

Then:

```text
H(H12 + H34) = MERKLE ROOT
```

Your Unit 2 PPT illustrates exactly this hierarchical hash structure. 

So:

> **Merkle root is a single hash representing the transactions in a block.**

This is important because it allows efficient verification of transaction inclusion.

We'll study Merkle trees much more deeply in the cryptography module.

# 17. What is a Nonce?

A nonce is a value used in the block creation/mining process.

In Proof of Work systems, miners repeatedly change the nonce to search for a block hash satisfying the required condition.

Simplified:

```text
Block data + Nonce 1 → Hash ❌
Block data + Nonce 2 → Hash ❌
Block data + Nonce 3 → Hash ❌
...
Block data + Nonce N → Hash ✅
```

Then the block can satisfy the PoW requirement.

⚠️ Don't confuse this with the **nonce in encryption protocols**. Your Unit 2 PPT uses nonce more generally as a value that can be used once in a cryptographic protocol. 

In blockchain/Bitcoin context, the nonce is particularly associated with the mining/PoW search.

# 22. HOW BLOCKCHAIN WORKS ⭐⭐⭐⭐⭐

This is **one of the most important things in this entire module**.

Your PPT gives the exact sequence:

```text
1. Transaction is initiated
          ↓
2. Transaction is validated and broadcast
          ↓
3. Find new block
          ↓
4. New block found
          ↓
5. Add new block to blockchain
```



Now understand every step.

---

## STEP 1 — Transaction is initiated

Suppose Alice wants to send Bob some cryptocurrency.

Alice creates a transaction.

The transaction contains information such as:

```text
Sender
Receiver
Amount
Other validation information
```

The transaction is digitally signed using Alice's private key.

Your PPT explicitly describes transaction creation and signing using the private key. 

---

## STEP 2 — Transaction is validated and broadcast

The transaction is propagated to other nodes.

Your PPT mentions data-dissemination mechanisms such as the **Gossip protocol**.

Nodes receive the transaction and check it against validity criteria. 

Conceptually:

```text
Alice
  ↓
Transaction
  ↓
Node
  ↓
Broadcast
 ↙ ↓ ↘
N1 N2 N3
```

---

## STEP 3 — Find New Block

Validated transactions are included in a block.

In PoW-based blockchains such as Bitcoin, miners work on finding/finalizing the block.

Your PPT describes miners racing to finalize their blocks through mining. 

---

## STEP 4 — New Block Found

The miner/participant satisfies the requirements of the consensus mechanism.

In Bitcoin's PoW case, this involves solving the required mathematical puzzle.

The block is then considered found/finalized, and the transaction is considered confirmed.



---

## STEP 5 — Add Block to Blockchain

The newly created block is:

1. Validated
2. Transactions/smart contracts executed
3. Propagated to peers
4. Validated by peers
5. Added to the ledger

Then the next block cryptographically links back to it using a hash pointer.
