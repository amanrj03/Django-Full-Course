# 1. Digital Signature ⭐⭐⭐⭐⭐

First make this absolutely clear:

> A **digital signature** is a cryptographic mechanism that allows a signer to prove that a message was signed using their private key and allows others to verify it using the corresponding public key.

Your PPT states:

> **Signer → private key**

> **Verifier → signer's public key** 

### Basic process

```text id="5g1x7d"
                 MESSAGE
                    │
                    ↓
                  HASH
                    │
                    ↓
             MESSAGE DIGEST
                    │
                    ↓
          Sign with PRIVATE KEY
                    │
                    ↓
           DIGITAL SIGNATURE
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
       Message             Signature
          │                   │
          └─────────┬─────────┘
                    ↓
                VERIFIER
                    │
             PUBLIC KEY
                    ↓
              Verification
```

---

# 2. Why Hash the Message Before Signing?

Suppose the message is extremely large:

```text
10 MB message
```

Instead of directly signing the entire message, we can:

```text
10 MB message
      ↓
    HASH
      ↓
Fixed-size digest
      ↓
    SIGN
```

This makes the signing operation more efficient.

Your PPT specifically includes **RSA signature on the message digest**. 

---

# 3. What Does a Digital Signature Provide?

The major properties you should remember are:

### 1. Authentication

Helps establish who signed the message.

### 2. Integrity

If the message is modified, signature verification should fail.

### 3. Non-repudiation

Provides evidence that can help prevent the signer from credibly denying the signing action.

### Easy memory:

> **A-I-N**

**A**uthentication
**I**ntegrity
**N**on-repudiation

---

# 4. Digital Signature vs Encryption

This is an extremely common exam question.

| Digital Signature                       | Encryption                            |
| --------------------------------------- | ------------------------------------- |
| Provides authentication/integrity       | Provides confidentiality              |
| Sign with private key                   | Encrypt using receiver's public key   |
| Verify with public key                  | Decrypt using receiver's private key  |
| Proves/signifies origin of message      | Hides message contents                |
| Used heavily in blockchain transactions | Used when confidentiality is required |

### Remember:

```text id="0vqh4k"
SIGNATURE:
Private → Sign
Public  → Verify

ENCRYPTION:
Public  → Encrypt
Private → Decrypt
```

# 6. Blind Signature ⭐⭐⭐⭐⭐

The idea is very interesting:

> The signer signs a message **without actually seeing the message**.

Your PPT says the message is first disguised/blinded before signing. 

Conceptually:

```text id="qj7j1d"
Original Message
       ↓
    BLINDING
       ↓
Blinded Message
       ↓
     SIGN
       ↓
Blind Signature
       ↓
    UNBLIND
       ↓
Signature on original message
```

The signer never learns the original content.

---

# 7. Why Blind Signatures?

One important application mentioned in your PPT:

> **Digital cash**

Blind signatures can allow someone to obtain a valid signature without revealing the underlying message/value to the signer.

Your PPT also mentions Blindcoin/Mixcoin-related use for hiding addresses from a mixing service. 

### Exam definition:

> **A blind signature allows a signer to sign a message without learning the message itself.**

---

# 8. Multisignature — Multi-Sig ⭐⭐⭐⭐⭐

A multisignature scheme allows:

> **Multiple users to sign one message/transaction.**

Your PPT says multiple unique keys held by different owners can be used to sign a single message. 

Example:

```text id="w4xj4m"
Alice ──┐
Bob   ──┼──→ Transaction
Charlie ─┘
          ↓
     Multiple signatures
          ↓
       Authorized
```

---

# 9. Real-World Example of Multisig

Suppose a company wants **2 out of 3 directors** to approve a transaction.

```text id="k9e2qy"
Alice
Bob
Charlie

2 signatures required

Alice + Bob       → ACCEPT
Alice + Charlie   → ACCEPT
Bob + Charlie     → ACCEPT

Alice only        → REJECT
```

This increases security because one compromised key may not be enough.

Your PPT notes that multisignatures can set a required number of signatures to authorize transactions and have been implemented in Bitcoin. 

---

# 10. Threshold Signatures ⭐⭐⭐⭐⭐

Threshold signatures are related to secret sharing.

The basic concept is:

```text id="t6b3gy"
Private Key
     ↓
Split into shares
     ↓
┌────┬────┬────┬────┐
A    B    C    D
```

A required number of participants use their shares to participate in signing.

Your PPT emphasizes that threshold signatures split the private key into multiple parts, with each signer holding a share. 

---

# 11. Threshold vs Multisignature

This distinction can earn marks.

### Multisignature

```text id="fzr3yn"
Different users
     ↓
Different private keys
     ↓
Multiple signatures
```

### Threshold signature

```text id="8jrxzt"
One distributed private key
        ↓
Key shares
        ↓
Participants cooperate
        ↓
One resulting signature
```

Your PPT specifically says threshold signatures can produce **one digital signature** verified with **one public key**, resulting in smaller transactions and faster verification. 

---

# 12. Aggregate Signatures ⭐⭐⭐⭐⭐

Aggregate signatures combine multiple signatures into:

> **A single compact signature.**

Your PPT explains that the purpose is to reduce signature size when multiple signatures are used. 

Example:

```text id="s5w7lq"
Signature A ─┐
Signature B ─┼──→ AGGREGATION → One signature
Signature C ─┘
```

The verifier can use the aggregate signature to verify that the relevant users signed their messages.

---

# 13. Aggregate Signature Example

Suppose:

```text id="0m3qwb"
Message A → Signature A
Message B → Signature B
Message C → Signature C
```

Without aggregation:

```text
A + B + C = 3 signatures
```

With aggregation:

```text
A + B + C
    ↓
One aggregate signature
```

This reduces communication/storage overhead.

Your PPT gives **Boneh–Lynn–Shacham (BLS)** aggregate signatures as a popular example and notes their use in blockchains, including Ethereum 2.0. 

---

# 14. Multisignature vs Threshold vs Aggregate

🔥 **Memorize this table.**

| Type               | Main idea                                                  |
| ------------------ | ---------------------------------------------------------- |

| **Multisignature** | Multiple users sign one message                            |
| **Threshold**      | Key divided into shares; sufficient participants cooperate |
| **Aggregate**      | Multiple signatures combined into one compact signature    |

# 15. Commitment Schemes ⭐⭐⭐⭐⭐

Your PPT describes commitment schemes as the cryptographic equivalent of a **sealed envelope**. 

Imagine:

```text id="b8u4m5"
Alice chooses a secret value
          ↓
     Put it in sealed
       envelope
          ↓
      COMMIT
          ↓
Later...
          ↓
       OPEN
          ↓
      Reveal value
```

The commitment itself should not reveal the actual value.

---

# 16. Two Phases of Commitment

Your PPT explicitly identifies:

### 1. Commit phase

The sender commits to the value.

### 2. Open phase

The sender reveals the value and information needed for verification.



### Easy memory:

> **Commit → Hide**

> **Open → Reveal**

---

# 17. Properties of Commitment Schemes

The two important conceptual properties are:

### Hiding

The commitment doesn't reveal the committed value.

### Binding

After committing, the sender should not be able to change the value.

Think:

```text id="xsk8jw"
COMMIT
  ↓
"I choose X"
  ↓
Cannot secretly change X → Y
```

# 19. Base64

Base64 converts binary data into printable characters.

Your PPT states:

> Base64 is used to encode binary data into printable characters. 

Conceptually:

```text id="a7i3ka"
Binary data
    ↓
 Base64
    ↓
Printable characters
```

### Important:

Base64 **doesn't provide secrecy**.

Anyone can decode Base64.

---

# 20. Base58 ⭐⭐⭐⭐⭐

Base58 is particularly relevant to Bitcoin.

Your PPT says Base58 was first introduced with Bitcoin and is used to encode integers into alphanumeric strings. 

Why?

It avoids confusing characters.

For example:

```text id="9h6d5n"
0  O
1  I
l
```

Characters that can easily be confused are avoided.

This is useful for Bitcoin addresses because confusing characters could result in sending funds to an incorrect address. 

---

# 21. Base64 vs Base58

| Base64                 | Base58                                       |
| ---------------------- | -------------------------------------------- |
| Encodes binary data    | Used for compact alphanumeric representation |
| Printable characters   | Avoids visually confusing characters         |
| Common in many systems | Strongly associated with Bitcoin addresses   |
| Not encryption         | Not encryption                               |

# 23. Merkle Tree ⭐⭐⭐⭐⭐

A Merkle tree is a tree structure where hashes are used to summarize data.

Suppose we have four transactions:

```text id="s4v2bb"
T1     T2     T3     T4
│      │      │      │
Hash   Hash   Hash   Hash
 \      /       \     /
  H12             H34
      \           /
        ROOT
```

The root is called the:

> **Merkle Root**

---

# 24. Why Merkle Trees?

They allow efficient verification of whether a particular transaction belongs to a set of transactions.

Instead of sending every transaction:

```text id="h9k2g1"
T1 T2 T3 T4 T5 T6 T7 T8
```

you can provide a relatively small set of hashes forming a **Merkle proof**.

This is particularly useful for blockchain data structures.

---

# 25. Patricia Tree

Your PPT lists **Patricia Tree** as another application of cryptographic hash functions. 

For your exam, remember:

> **Patricia trees are trie-based data structures used to efficiently store and retrieve key-value information.**

They are especially important in blockchain systems such as Ethereum.

---
