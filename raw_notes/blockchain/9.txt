# Topic 1: Distributed systems — the foundation

Before understanding consensus, we need to understand what a distributed system is.

## 1.1 What is a distributed system?

A distributed system is a collection of independent computers that communicate and coordinate with one another to perform a task.

Each computer can process information independently, but the computers cooperate to provide a common service.

For example, imagine a banking system with three computers:

Banking application

A user requests a money transfer.

Node A

Balance data

Node B

Transaction log

Node C

Backup copy

The nodes communicate to keep the system consistent.

Here, a node is a computer or process participating in the system.

A distributed system offers several benefits:

- Reliability: the system can continue operating despite some failures.
- Availability: services may remain accessible when some nodes fail.
- Scalability: additional computers can contribute resources.
- Replication: multiple nodes can maintain copies of data.

However, distributed systems also face a problem: different computers may have different information at the same time.

### Example

Suppose Node A receives a transaction first, but Node C receives it two seconds later. During those two seconds, their local records may differ.

This can happen because of:

- Network delays
- Lost messages
- Failed computers
- Faulty or malicious participants

This is why distributed systems need mechanisms to coordinate their decisions.

# Topic 2: What is consensus?

## 2.1 Basic meaning

The word consensus means agreement.

In a distributed system, consensus is the process through which participating nodes agree on a common decision or value according to a defined protocol.

In blockchain, nodes need to agree on which transactions and blocks are accepted and on the resulting ledger state.

### Simple example

Suppose four nodes must decide whether a transaction should be accepted.

Proposed transaction

Aman sends 2 coins to Rahul.

Node A

Valid

Node B

Valid

Node C

Valid

Node D

Valid

Common decision: Accept the transaction

The nodes don't necessarily need to receive messages simultaneously. They need to follow the protocol so that honest participants reach compatible decisions under the protocol's assumptions.

Important: Consensus is not always a simple majority vote. Different algorithms use different mechanisms, including voting, cryptographic proofs, and computational work.

## 2.2 Why does blockchain need consensus?

Consider a digital currency without a central bank or administrator. If different nodes maintain different transaction histories, they may disagree about who owns the funds.

Consensus helps solve the following problems:

1. Agreement: nodes need to agree on the accepted ledger history.
2. Double spending: the same funds must not be spent successfully twice.
3. Fault tolerance: the system should cope with some failed or malicious nodes.
4. Consistency: replicated ledgers should converge on a compatible state.
5. Transaction ordering: conflicting transactions need to be handled consistently.

Your teacher's PPT identifies Bitcoin as a public blockchain using Proof of Work, also known as Nakamoto consensus, and contrasts it with traditional consensus approaches used by many permissioned blockchains.&#x20;

## 2.3 A crucial distinction: validation vs consensus

These terms are related but not identical.

| Validation                                                                     | Consensus                                                          |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| Checks whether a transaction or block follows protocol rules.                  | Determines which proposed blocks or decisions the network accepts. |
| Checks signatures, balances or other required conditions.                      | Coordinates agreement across distributed nodes.                    |
| A transaction can pass validation but still conflict with another transaction. | The consensus protocol helps determine the accepted history.       |

Remember: validation checks the rules; consensus coordinates agreement.

# Topic 3: The Byzantine Generals Problem

This is one of the most important concepts in consensus algorithms and a strong candidate for a 5-mark or 10-mark theory question.

## 3.1 What is the Byzantine Generals Problem?

The Byzantine Generals Problem is a classic problem in distributed computing that explains how a group of participants can reach a common decision when some participants may be faulty or deliberately dishonest.

Your teacher's CONSENSUS UNIT-3.pptx uses the military analogy of generals coordinating an attack or retreat.&#x20;

CONSENSUS UNIT-3.pptx



### Understand the story

Imagine an army surrounding a city. Three generals command different army units. They must decide whether to attack or retreat.

They communicate through messengers because they are in different locations.

However, one general may be a traitor and send contradictory messages.

Commander

Sends conflicting instructions

General A

Receives "Attack"

General B

Receives "Retreat"

Problem: How can the loyal generals agree on one decision despite the traitor?

If loyal generals follow conflicting instructions, the army may fail even though most generals are honest.

The challenge is to design a protocol that allows the honest participants to agree despite a limited number of malicious participants.

## 3.2 Mapping the problem to blockchain

| Military example               | Blockchain equivalent                |
| ------------------------------ | ------------------------------------ |
| General                        | Node or validator                    |
| Attack or retreat              | Accept or reject a proposed decision |
| Messenger                      | Network message                      |
| Traitor                        | Malicious or Byzantine node          |
| Agreement among loyal generals | Agreement among honest nodes         |
| Common battle plan             | Consistent ledger decision           |

For example, a malicious blockchain node might claim that one transaction is valid to one node but tell another node that a conflicting transaction should be accepted.

A Byzantine fault-tolerant protocol is designed to handle this kind of behaviour within its specified fault threshold.

## 3.3 What is a Byzantine fault?

A Byzantine fault is an arbitrary fault in which a node may behave incorrectly in many possible ways, including deliberately malicious behaviour.

Examples:

- Sending conflicting messages to different nodes
- Sending invalid data
- Failing to follow the protocol
- Pretending to have accepted a decision when it has not
- Cooperating with other malicious nodes to disrupt agreement

This is more difficult to handle than a computer that simply crashes.

## 3.4 What is the solution idea?

Consensus algorithms use rules that help honest nodes distinguish acceptable decisions from conflicting or invalid ones.

Depending on the algorithm, these rules can involve:

- Collecting messages from multiple participants
- Counting votes or obtaining a quorum
- Using cryptographic signatures to verify message origins
- Requiring enough independent participants to confirm a decision
- Ignoring decisions that fail the protocol's conditions

No protocol can tolerate an unlimited number of faulty nodes. Its guarantees depend on the algorithm and the assumptions about how many nodes may be faulty.

### Exam-ready 5-mark answer

Question: Explain the Byzantine Generals Problem and its relevance to blockchain.

The Byzantine Generals Problem describes the difficulty of achieving agreement in a distributed system when some participants may be faulty or malicious. In the classical example, several generals must agree on whether to attack or retreat, but a traitorous general may send conflicting messages. This can cause honest generals to make inconsistent decisions.

In blockchain, generals correspond to nodes, messengers correspond to network messages, and traitors correspond to malicious nodes. A Byzantine fault-tolerant consensus algorithm enables honest participants to reach a consistent decision despite a limited number of faulty participants.

Thus, the problem provides the foundation for understanding Byzantine Fault Tolerance (BFT) and consensus algorithms used in distributed systems.

# Topic 4: Fault Tolerance — CFT vs BFT

## 4.1 What is fault tolerance?

Fault tolerance is the ability of a system to continue operating correctly even when some of its components fail.

For example, if one server stops working but the remaining servers continue to provide the service, the system demonstrates fault tolerance.

Your teacher's PPT classifies fault-tolerant consensus into two major categories:

- Crash Fault Tolerance (CFT)
- Byzantine Fault Tolerance (BFT)&#x20;

  CONSENSUS UNIT-3.pptx



## 4.2 Crash Fault Tolerance (CFT)

CFT handles nodes that fail in relatively predictable ways, such as crashing or stopping communication.

Imagine five servers maintaining copies of a database. One server suddenly switches off. The remaining servers can still reach a decision using the protocol's rules.

The failed server does not deliberately send contradictory information; it simply stops functioning or communicating.

Example algorithms: Paxos and Raft, as covered in your teacher's consensus material.

## 4.3 Byzantine Fault Tolerance (BFT)

BFT handles more complex failures, including arbitrary and malicious behaviour.

Imagine five validators. One validator sends conflicting messages to different participants, while another sends invalid information. The protocol must still protect agreement within its fault-tolerance assumptions.

Example algorithm: Practical Byzantine Fault Tolerance (PBFT).

## 4.4 CFT vs BFT — important comparison

| Feature                                 | CFT                                          | BFT                                                       |
| --------------------------------------- | -------------------------------------------- | --------------------------------------------------------- |
| Full form                               | Crash Fault Tolerance                        | Byzantine Fault Tolerance                                 |
| Type of failure                         | Nodes crash or stop responding               | Nodes may behave arbitrarily or maliciously               |
| Handles conflicting malicious messages? | Not designed to tolerate Byzantine behaviour | Designed to tolerate it within its fault threshold        |
| Typical algorithm                       | Paxos, Raft                                  | PBFT                                                      |
| Complexity                              | Usually simpler                              | Usually more complex                                      |
| Communication overhead                  | Often lower                                  | Often higher                                              |
| Common application                      | Replicated databases and services            | Distributed systems with potentially untrusted validators |

### Easy memory trick

- CFT = Crash
- BFT = Bad behaviour

BFT covers a broader and more difficult class of faults.

## 4.5 What does \\(F\\) mean?

In consensus algorithms, \\(F\\) commonly denotes the maximum number of faulty nodes the protocol is designed to tolerate.

For example, if a protocol is designed to tolerate one faulty node, then \\(F=1\\).

The number of nodes needed depends on the fault model and the particular algorithm. We'll derive the important formulas later in this module.

# Topic 5: Replication and State Machine Replication

## 5.1 What is replication?

Replication means maintaining copies of the same data or system state on multiple nodes.

Why do we need it?

Suppose a blockchain stores all its data on only one computer. If that computer fails, the ledger may become unavailable.

Instead, multiple nodes maintain copies of the ledger.

Transaction history

Copy A

Copy B

Copy C

Multiple nodes store replicas of the system state.

Replication improves availability and fault tolerance. However, merely copying data is not enough: the copies must be updated consistently.

For example, if Node A processes a transfer before Node B does, both nodes need to process the relevant transactions in a compatible order.

This is where consensus and replication work together.

## 5.2 Types of replication

Your teacher's PPT mentions two replication techniques: active replication and passive replication.&#x20;

CONSENSUS UNIT-3.pptx



### A. Active replication

In active replication, multiple replicas process the same requests in the same order.

The replicas independently execute the requests and should reach the same state, assuming they start from the same state and process requests deterministically.

```
             Client request
                   │
          Ordered broadcast
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
        Node A   Node B   Node C
        Execute  Execute  Execute
          │        │        │
          ▼        ▼        ▼
         Same resulting state
```

Key point: all replicas actively execute the ordered requests.

### B. Passive replication

In passive replication, a primary node processes requests and communicates the relevant state changes to backup replicas.

```
             Client request
                   │
                   ▼
              Primary
             processes it
                   │
          State updates sent
             ┌─────┴─────┐
             ▼           ▼
          Backup A    Backup B
```

Key point: the primary performs the main processing, while backups maintain the state and can support recovery.

| Active replication                              | Passive replication                                 |
| ----------------------------------------------- | --------------------------------------------------- |
| Multiple replicas execute requests.             | Primary processes requests and sends state updates. |
| Requires requests to be ordered consistently.   | Depends on reliable state updates from the primary. |
| Replicas actively maintain the resulting state. | Backups maintain state and support recovery.        |

## 5.3 What is state machine replication?

A state machine is a model of a system that has a current state and changes that state when it receives an input.

Consider a simple bank account:

- Initial state: balance = ₹1,000
- Input: deposit ₹500
- New state: balance = ₹1,500

Mathematically, we can represent this as:

\\[ S\_{new}=f(S\_{current},Input) \\]

Here, \\(f\\) is the operation that determines the next state.

### State machine replication (SMR)

State machine replication means maintaining multiple copies of a state machine and ensuring that they process the same requests in the same order.

If all replicas begin with the same state and deterministically execute the same ordered requests, they should arrive at the same final state.

Your teacher's PPT describes a primary/backup approach in which requests are broadcast in a total order so replicas process them in the same sequence. It also connects total-order broadcast with distributed consensus.&#x20;

CONSENSUS UNIT-3.pptx



### Why is request ordering important?

Suppose an account contains ₹1,000 and receives two operations:

1. Withdraw ₹800.
2. Withdraw ₹500.

If the first withdrawal happens before the second, the second must fail for insufficient funds.

If replicas process the operations in inconsistent orders, they may reach inconsistent outcomes. Consensus and ordered processing help prevent that.

### Exam definition

State machine replication is a fault-tolerance technique in which multiple replicas of a state machine process the same ordered requests to maintain a consistent system state.

# Topic 6: Properties of Consensus — Safety and Liveness

This is a particularly important exam topic because it explains what a correct consensus algorithm must guarantee.

Your teacher's PPT divides the requirements into safety and liveness, with agreement, validity, integrity and termination as the associated properties.&#x20;

CONSENSUS UNIT-3.pptx



## 6.1 What is safety?

Safety means, broadly, nothing incorrect happens.

A consensus protocol must prevent honest nodes from deciding on conflicting values.

Three properties are especially important.

### A. Agreement

No two honest processes should decide on different values.

Example: if the protocol decides to accept Block A, another honest node must not decide to accept a conflicting Block B for the same decision.

### B. Validity

The value decided must satisfy the protocol's validity condition.

In the formulation used in your teacher's PPT, a decided value must have been proposed by a process; it cannot simply appear from nowhere. In blockchain, validity additionally involves checking protocol rules for transactions and blocks.

### C. Integrity

A process must not decide more than once in a single consensus instance.

For example, a validator should not decide one value and then decide a conflicting value for the same decision.

## 6.2 What is liveness?

Liveness means, broadly, something good eventually happens.

A key property is:

### D. Termination

Every honest node should eventually reach a decision, provided the algorithm's required assumptions hold.

A protocol that preserves agreement forever but never reaches a decision has a liveness problem.

## 6.3 Safety vs liveness

| Property        | Safety                                      | Liveness                                         |
| --------------- | ------------------------------------------- | ------------------------------------------------ |
| Main idea       | Nothing bad happens.                        | Something good eventually happens.               |
| Focus           | Prevent conflicting or invalid decisions.   | Ensure the protocol makes progress.              |
| Example failure | Two honest nodes decide conflicting blocks. | Nodes wait indefinitely and no block is decided. |
| Key terms       | Agreement, validity, integrity              | Termination                                      |

Memory trick: A–V–I–T

- Agreement — same decision
- Validity — permitted decision
- Integrity — decide only once
- Termination — eventually decide

Agreement, validity and integrity are safety properties in the presentation's framework; termination is the liveness property.

### Important nuance

Safety and liveness are separate guarantees. A protocol may preserve safety while temporarily making no progress during a network problem. Whether it eventually makes progress depends on its assumptions and recovery mechanisms.

### Exam-ready 5-mark answer

Question: Explain safety and liveness properties of consensus algorithms.

A consensus algorithm must maintain safety and liveness to provide reliable agreement in a distributed system.

1. Agreement: no two honest processes decide on different values.
2. Validity: the decided value must satisfy the protocol's validity requirements.
3. Integrity: a process decides only once in a consensus instance.
4. Termination: every honest process eventually reaches a decision under the protocol's assumptions.

Safety prevents incorrect or conflicting decisions, whereas liveness ensures that the system makes progress. Both are essential for reliable distributed consensus.

# Topic 7: Analysis and Design of Consensus Algorithms

Now let's understand the second major phrase in your syllabus: analysis and design.

## 7.1 What does designing a consensus algorithm mean?

Before creating a consensus algorithm, we must define the environment in which it will operate.

Your teacher's PPT identifies three important aspects of a computational model:

1. Processes
2. Network conditions
3. Timing assumptions

These assumptions help us analyse whether an algorithm will work correctly.&#x20;

CONSENSUS UNIT-3.pptx



### 1. Processes

A process is an executing participant in a distributed system.

We must decide:

- How many nodes participate?
- Can nodes crash?
- Can nodes behave maliciously?
- Are all nodes trusted or are some potentially faulty?

For example, a private company network might contain a known set of validators, while a public blockchain permits unknown participants.

### 2. Network conditions

Nodes communicate using messages, but messages may be delayed, lost or delivered at different times.

We must consider:

- Whether messages are delivered reliably
- Whether nodes can communicate with every other node
- Whether network partitions may occur
- Whether nodes receive messages in different orders

### 3. Timing assumptions

We must decide what the algorithm assumes about the time required to send messages and execute operations.

This leads to three models: synchronous, asynchronous and partially synchronous.

We'll study them in Topic 8.

## 7.2 What do we measure when analysing an algorithm?

A consensus algorithm can be evaluated using several criteria.

| Criterion              | What it asks                                             |
| ---------------------- | -------------------------------------------------------- |
| Safety                 | Can honest nodes decide conflicting values?              |
| Liveness               | Can the system eventually decide?                        |
| Fault tolerance        | How many faulty nodes can it tolerate?                   |
| Latency                | How long does a decision take?                           |
| Communication overhead | How many messages must nodes exchange?                   |
| Scalability            | Does performance remain acceptable as the network grows? |
| Resource cost          | How much energy, computation and storage are required?   |

A consensus algorithm is not necessarily best simply because it is fast. A fast protocol that cannot tolerate the failures relevant to an application may be unsuitable.

### Example: choosing for two systems

Consider two applications:

- Application A: a consortium of five known banks wants fast transaction finality.
- Application B: a public cryptocurrency allows anyone to join and does not want to depend on a fixed set of trusted validators.

These systems have different trust models and participation requirements. They may therefore choose different consensus mechanisms.

That is the central idea behind analysis and design: first understand the system's requirements, then select a protocol that satisfies them.

# Topic 8: Synchronous, Asynchronous and Partially Synchronous Networks

This is an important theory topic and a foundation for understanding FLP impossibility.

## 8.1 Synchronous network

A synchronous network assumes that there is a known upper bound on communication and processing delays.

For example, suppose a system assumes that a message will arrive within 100 milliseconds under the model's conditions.

If the expected time passes without a response, the algorithm can use that timing assumption when deciding how to proceed.

Key point: the maximum delay is known.

## 8.2 Asynchronous network

An asynchronous network makes no fixed upper-bound assumption about communication or processing delays.

A message might arrive quickly, or it might take a very long time.

If a node does not receive a response, it cannot always distinguish between:

- A failed node
- A delayed message
- A slow process

This uncertainty makes consensus difficult.

Key point: no known upper bound on delay.

## 8.3 Partially synchronous network

A partially synchronous network lies between the two.

The delays may be unpredictable, or the upper bound may exist but be unknown to the nodes. In an eventual-synchrony model, the network eventually behaves synchronously for long enough that the protocol can make progress.

Your teacher's PPT calls the time after which the network becomes sufficiently synchronous the Global Stabilization Time (GST). Nodes do not know the exact GST in advance.&#x20;

CONSENSUS UNIT-3.pptx



Key point: the system may initially behave asynchronously but eventually provides sufficiently predictable communication.

## 8.4 Comparison table

| Feature              | Synchronous                  | Asynchronous                                | Partially synchronous                         |
| -------------------- | ---------------------------- | ------------------------------------------- | --------------------------------------------- |
| Upper bound on delay | Known                        | No known bound                              | May exist but be unknown, or apply eventually |
| Message timing       | Predictable within the model | Unpredictable                               | Initially unpredictable; may later stabilise  |
| Failure detection    | Timing assumptions help      | Difficult to distinguish delay from failure | Becomes more practical after stabilisation    |
| Key term             | Known delay bound            | No timing bound                             | GST in eventual-synchrony models              |

### Real-life analogy

Imagine sending a message to a friend:

- Synchronous: you know your friend's reply will arrive within a fixed time.
- Asynchronous: you have no guarantee about when the reply will arrive.
- Partially synchronous: replies may initially be delayed, but the connection eventually becomes stable.

# Topic 9: FLP Impossibility

## 9.1 What is the FLP result?

The FLP impossibility result, named after Fischer, Lynch and Paterson, establishes a fundamental limitation in distributed computing.

In simplified terms, it proves that no deterministic consensus algorithm can guarantee termination in every possible execution of a fully asynchronous message-passing system if even one process may crash, under the model's assumptions.

This does not mean that consensus is impossible in practice.

It means that a deterministic protocol cannot guarantee that it will always terminate under every allowed asynchronous execution while also meeting the required consensus properties.

Your teacher's PPT explicitly includes FLP impossibility and lists common approaches used to address its practical implications.&#x20;

CONSENSUS UNIT-3.pptx



## 9.2 Why does this happen?

Suppose Node A proposes a value and waits for Node B's response.

No response arrives.

Node A cannot know with certainty whether:

1. Node B has crashed.
2. Node B is still running, but its message is delayed.

If A decides without B, it may risk violating agreement in some execution. If A waits indefinitely, it may violate termination.

This uncertainty is at the heart of the problem.

## 9.3 How do practical systems address this limitation?

Your teacher's PPT lists three approaches:

1\. Failure detectors

Components attempt to detect or suspect failed processors. In practice, such detectors can be imperfect because slow nodes may look like failed nodes.

2\. Randomized algorithms

Random choices can help a protocol make progress in situations where deterministic choices cannot guarantee termination under the same assumptions.

3\. Synchrony assumptions

Protocols may assume bounded delays or eventual synchrony so that they can eventually make progress.

### Exam-ready answer

Question: Explain the FLP impossibility result and its implications for consensus algorithms.

The FLP impossibility result states that deterministic consensus cannot guarantee termination in every execution of a fully asynchronous message-passing system if a process may crash, under the result's assumptions.

In an asynchronous network, a node cannot reliably distinguish a crashed process from one whose message is delayed indefinitely. Waiting may prevent termination, while deciding without sufficient information may threaten agreement.

Practical approaches include failure detectors, randomized algorithms and synchrony assumptions. The result highlights the trade-off between making progress and maintaining correctness under unpredictable network conditions.

# Topic 10: Minimum Number of Nodes for Fault Tolerance

Your teacher's PPT includes two important formulas for the minimum number of nodes required under crash and Byzantine fault models. These are worth memorising for theory questions and numerical problems.

## 10.1 Crash Fault Tolerance

For the CFT lower bound covered in your PPT:

\\[ \boxed{N\geq 2F+1} \\]

Where:

- \\(N\\) = total number of nodes
- \\(F\\) = maximum number of crash failures to tolerate

### Example

If the system must tolerate one crashed node:

\\[ N\geq 2(1)+1=3 \\]

Therefore, at least 3 nodes are required under this bound.

With 3 nodes, the system can tolerate one crash failure while retaining a majority of 2 functioning nodes.

## 10.2 Byzantine Fault Tolerance

For the BFT lower bound in your PPT:

\\[ \boxed{N\geq 3F+1} \\]

### Example

If the system must tolerate one Byzantine node:

\\[ N\geq 3(1)+1=4 \\]

Therefore, at least 4 nodes are required under this bound.

The difference arises because Byzantine nodes can behave maliciously and send conflicting messages, making the problem harder than simply handling crashed nodes.

Your teacher's slides state the lower bounds as \\(2F+1\\) for CFT and \\(3F+1\\) for BFT.&#x20;
