# Module 19 — Testing in Django

Now we move to **Testing**, the final topic of Unit III.

So far, we've learned how to:

```text
URLs → Views → Templates → Dynamic Data → Debugging
```

But how do we know that our application actually works correctly?

That's where **testing** comes in.

---

# 1. What Is Software Testing?

**Software testing** is the process of checking whether software behaves as expected.

Suppose we create:

```python
def add(a, b):
    return a + b
```

We expect:

```text
add(2, 3) → 5
```

A test verifies that assumption.

In Django, we can automatically test:

* Views
* URLs
* Templates
* Models
* Forms
* Authentication
* HTTP responses
* Application logic

---

# 2. Why Do We Need Testing?

Imagine your Django application has:

```text
100 views
500 URLs
50 forms
20 models
```

You cannot manually check every feature every time you modify the application.

Suppose you change the login system.

It might accidentally break:

```text
Registration
Profile
Dashboard
Logout
```

Automated tests help detect these regressions.

---

# 3. What Is a Test?

A test generally follows:

```text
Arrange
   ↓
Act
   ↓
Assert
```

### Arrange

Prepare the required data.

### Act

Perform the operation.

### Assert

Check whether the result is what you expected.

Example:

```python
result = add(2, 3)

self.assertEqual(result, 5)
```

Here:

```text
Act → add(2, 3)
Assert → result == 5
```

---

# 4. What Is Unit Testing?

**Unit testing** tests a small, isolated part of an application.

For example:

```python
def calculate_total(price, quantity):
    return price * quantity
```

We could test this function independently.

```python
self.assertEqual(
    calculate_total(100, 5),
    500
)
```

The goal is to verify individual units of behavior.

---

# 5. Django Testing Framework

Django provides built-in support for testing.

A newly created Django app normally contains:

```text
students/
├── admin.py
├── apps.py
├── models.py
├── tests.py
├── views.py
└── ...
```

The default:

```text
tests.py
```

is where you can begin writing tests.

Django's testing system is built on Python's `unittest` framework.

# 6. Basic Django Test

Suppose our `views.py` contains:

```python
from django.http import HttpResponse

def home(request):
    return HttpResponse("Hello Django")
```

We can write:

```python
from django.test import TestCase

class HomeTest(TestCase):

    def test_home(self):
        response = self.client.get("/")

        self.assertEqual(response.status_code, 200)
```

Let's understand every line.

---

# 7. `TestCase`

```python
from django.test import TestCase
```

`TestCase` provides Django-specific testing functionality.

Then:

```python
class HomeTest(TestCase):
```

creates a test class.

It inherits from Django's `TestCase`.

---

# 8. Test Method

Inside the class:

```python
def test_home(self):
```

This is a test method.

Django's test discovery looks for methods whose names begin with:

```text
test
```

So:

```python
def test_home(self):
```

is detected as a test.

---

# 9. Django Test Client

This is extremely important:

```python
self.client
```

Django provides a **test client** that can simulate requests to your application.

For example:

```python
response = self.client.get("/")
```

This behaves conceptually like a browser making a GET request.

You don't need to manually open Chrome.

---

# 10. GET Request Test

Example:

```python
response = self.client.get("/")
```

This sends a GET request to:

```text
/
```

Then we can inspect:

```python
response.status_code
```

If the page works:

```text
200
```

---

# 11. `assertEqual`

We can write:

```python
self.assertEqual(
    response.status_code,
    200
)
```

This means:

> Assert that the response status code equals 200.

If it is:

```text
200
```

the test passes.

If it is:

```text
404
```

the test fails.

# 14. What Is the Test Database?

When Django tests interact with the database, Django creates a **separate test database**.

This prevents normal development data from being modified by tests.

Conceptually:

```text
Normal Database
      │
      │ protected
      ↓
Test Database
      │
      ↓
Tests run here
      │
      ↓
Test database is removed
```

This is an important Django testing feature.

---

# 15. Why Not Use the Real Database?

Imagine your database contains:

```text
1000 students
```

A test might create:

```text
Student: Test Student
```

If tests used your real database, they could modify or delete real data.

Therefore Django isolates testing using a test database.

```python
def test_home_content(self):
```


# 21. Testing URL Names

Suppose:

```python
path(
    "students/",
    views.students,
    name="students"
)
```

You can use Django's URL reversing system in tests.

For example:

```python
from django.urls import reverse

url = reverse("students")

response = self.client.get(url)
```

Then:

```python
self.assertEqual(
    response.status_code,
    200
)
```

This is often better than hardcoding:

```python
"/students/"
```

because if the URL path changes but its name remains the same, the test doesn't need to change.

# 30. `setUp()`

Suppose many tests need the same data.

Instead of creating the data repeatedly:

```python
def test_one(self):
    ...

def test_two(self):
    ...

def test_three(self):
    ...
```

you can use:

```python
def setUp(self):
    ...
```

Example:

```python
class StudentTest(TestCase):

    def setUp(self):

        self.student = Student.objects.create(
            name="Aman"
        )

    def test_student_name(self):

        self.assertEqual(
            self.student.name,
            "Aman"
        )
```

`setUp()` runs before each test method.

---

# 31. Why `setUp()` Is Useful

Suppose you have 10 tests and all require:

```text
Student
Course
Teacher
```

You can prepare the common test data in `setUp()`.

This avoids duplication.

---

# 32. Important: Tests Are Independent

A good test should generally not depend on another test having run first.

For example:

```text
test_create_student
        ↓
test_delete_student
```

You shouldn't assume `test_create_student` always runs first.

Each test should establish the state it needs.

Django's `TestCase` helps isolate database state between tests.

# 34. Testing Invalid Behavior

Don't only test successful cases.

Suppose:

```text
Valid ID → 200
Invalid ID → 404
```

Test both.

Example:

```python
def test_invalid_student(self):

    response = self.client.get(
        "/student/999/"
    )

    self.assertEqual(
        response.status_code,
        404
    )
```

This is called testing an **edge/error case**.

---

# 35. Positive vs Negative Tests

### Positive test

Tests expected valid behavior.

```text
Valid request
→ 200
```

### Negative test

Tests invalid/unexpected input.

```text
Invalid request
→ 400/404/etc.
```

Both are important.

---

# 36. What Is Regression Testing?

Suppose your login system worked yesterday.

You modify the registration system.

After the modification, login accidentally breaks.

A test that previously passed now fails.

This helps detect a **regression**.

So:

> Regression testing checks that previously working functionality continues to work after changes.

Automated tests are particularly valuable for this.

---

# 37. Test-Driven Development

You may hear the term **TDD**.

TDD stands for:

> Test-Driven Development.

The simplified cycle is:

```text
Write failing test
       ↓
Write code
       ↓
Make test pass
       ↓
Refactor
       ↓
Repeat
```

This is a development methodology.

You don't need to use TDD for every Django project, but understand the concept for viva.

# 38. Complete Example — Testing a Home Page

### `views.py`

```python
from django.shortcuts import render

def home(request):

    return render(
        request,
        "home.html",
        {
            "name": "Aman"
        }
    )
```

### `urls.py`

```python
from django.urls import path
from . import views

urlpatterns = [
    path(
        "",
        views.home,
        name="home"
    ),
]
```

### `tests.py`

```python
from django.test import TestCase
from django.urls import reverse


class HomeTest(TestCase):

    def test_home_page(self):

        url = reverse("home")

        response = self.client.get(url)

        self.assertEqual(
            response.status_code,
            200
        )

        self.assertTemplateUsed(
            response,
            "home.html"
        )

        self.assertContains(
            response,
            "Aman"
        )
```

This is a very good beginner Django test.

# 42. Common Testing Mistakes

### Mistake 1

Forgetting:

```python
from django.test import TestCase
```

---

### Mistake 2

Naming test method incorrectly:

```python
def home_test(self):
```

Instead use:

```python
def test_home(self):
```

---

### Mistake 3

Using incorrect URL:

```python
self.client.get("/wrong/")
```

when the actual URL is:

```text
/students/
```

---

### Mistake 4

Expecting the wrong status:

```python
self.assertEqual(
    response.status_code,
    404
)
```

when the view should return 200.

---

### Mistake 5

Testing only successful cases.

Always consider invalid input and failure scenarios.

# 54. ⭐ Testing Strategy for a Django Application

For a typical Django project, you might test:

```text
              Django Application
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
      URLs          Views        Models
       │             │             │
       ↓             ↓             ↓
    Routing       Responses      Database
       │             │             │
       └─────────────┼─────────────┘
                     ↓
                   Forms
                     ↓
              Authentication
```

For example:

### URL tests

```text
Does /students/ resolve correctly?
```

### View tests

```text
Does the view return 200?
```

### Template tests

```text
Is students.html rendered?
```

### Content tests

```text
Does the response contain the student's name?
```

### Model tests

```text
Can a Student be created correctly?
```

### Form tests

```text
Does invalid input get rejected?
```

### Authentication tests

```text
Can a logged-in user access the dashboard?
```
