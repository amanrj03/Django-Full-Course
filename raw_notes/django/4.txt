# Module 4 — Django Project Structure

Now we're going to **open the Django project and understand every important file**.

This module is extremely important because teachers love asking:

> "What is the purpose of `settings.py`?"

> "What does `manage.py` do?"

> "What is `urls.py`?"

> "Why are there two `__init__.py` files?"

> "What is WSGI?"

> "What is ASGI?"

By the end, you should be able to look at a Django project and understand **what every file is doing**.

---

# 1. Our Django Project

Suppose we created:

```bash
python -m django startproject College
```

The structure is:

```text
College/
│
├── manage.py
│
└── College/
    ├── __init__.py
    ├── settings.py
    ├── urls.py
    ├── asgi.py
    └── wsgi.py
```

Let's understand it one file at a time.

---

# 2. Outer `College` Folder

The outer folder:

```text
College/
```

is simply the directory containing your Django project.

It contains:

```text
manage.py
College/
```

Think of it as the **container for your project**.

---

# 3. `manage.py`

We've already seen this.

```text
College/
│
├── manage.py
```

`manage.py` is a command-line utility for interacting with your particular Django project.

For example:

```bash
python manage.py runserver
```

```bash
python manage.py startapp students
```

```bash
python manage.py migrate
```

```bash
python manage.py makemigrations
```

```bash
python manage.py createsuperuser
```

So:

> **`manage.py` provides a convenient way to execute Django management commands for a specific project.**

---

# 4. Inner `College` Folder

Now:

```text
College/
│
└── College/
```

This inner folder is the **Python package containing the project's configuration**.

It contains:

```text
__init__.py
settings.py
urls.py
asgi.py
wsgi.py
```

This is where the main Django project configuration lives.

---

# 5. `__init__.py`

You'll see:

```text
__init__.py
```

This is a Python package file.

Its presence historically tells Python that the directory should be treated as a package. In modern Python, namespace packages can exist without it, but Django's generated project structure includes it.

For your Django course, the important point is:

> **`__init__.py` marks/helps define the directory as a Python package and allows package-related Python imports.**

Usually, you don't need to modify it.

---

# 6. `settings.py`

This is one of the **most important files in Django**.

It contains the configuration of your Django project.

For example:

```python
DEBUG = True
```

```python
INSTALLED_APPS = [
    ...
]
```

```python
MIDDLEWARE = [
    ...
]
```

```python
ROOT_URLCONF = 'College.urls'
```

```python
DATABASES = {
    ...
}
```

We'll study these settings throughout the course.

Think:

> **`settings.py` = project configuration**

---

Many things.

### Installed applications

### Middleware

### Debug mode

---

# 8. `DEBUG`

You'll see:

```python
DEBUG = True
```

during development.

When something goes wrong, Django can show detailed debugging information.

For example:

```text
Traceback
File
Line number
Error message
```

This is useful while developing.

But:

> **You should not run a production deployment with `DEBUG = True`.**

Why?

Because detailed error pages can expose sensitive information.

We'll discuss this more when we reach debugging and deployment concepts.

---

# 9. `INSTALLED_APPS`

Another extremely important setting:

```python
INSTALLED_APPS = [
    ...
]
```

It tells Django which applications are installed/enabled in the project.

Later, when we create an app:

```bash
python manage.py startapp students
```

we'll need to make Django aware of the app, commonly by adding its configuration to `INSTALLED_APPS`.

We'll cover this carefully in Module 5.

# 10. `DATABASES`

You will find something similar to:

```python
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
    }
}
```

This configures the database.

The default Django project uses:

> **SQLite**

for development.

Later, your syllabus has an entire topic on:

> Database configuration

We'll study:

```text
SQLite
MySQL
PostgreSQL
```

later.

---

# 11. `TEMPLATES`

`settings.py` also contains template configuration.

Conceptually:

```text
Django
  ↓
Template configuration
  ↓
HTML templates
```

Later, when we create HTML templates, this setting becomes important.

---

# 12. `urls.py`

Now we come to another extremely important file.

```text
College/
└── College/
    └── urls.py
```

This file contains the project's **URL configuration**.

For example, conceptually:

```python
urlpatterns = [
    ...
]
```

Django uses URL patterns to determine what should happen when a user visits a URL.

For example:

```text
/about/
```

could be connected to:

```text
about()
```

and:

```text
/students/
```

could be connected to:

```text
students()
```

We'll learn this in detail in **Unit II**.

---

# 13. Why Is `urls.py` Important?

Suppose the browser requests:

```text
/students/
```

Django needs to determine:

> "Which code should handle `/students/`?"

The URL configuration helps answer that question.

Conceptually:

```text
/students/
     ↓
urls.py
     ↓
students view
```

---

# 14. `ROOT_URLCONF`

Inside `settings.py`, you'll see something similar to:

```python
ROOT_URLCONF = 'College.urls'
```

This tells Django where the **root URL configuration** is located.

In this case:

```text
College.urls
```

means:

```text
College package
     ↓
urls.py
```

So Django knows where to start looking for URL patterns.

---

# 15. `wsgi.py`

Now we have:

```text
wsgi.py
```

WSGI stands for:

> **Web Server Gateway Interface**

It is a standard interface between Python web applications/frameworks and web servers.

You don't need to master deployment yet.

For your current level, remember:

> **WSGI provides a standard interface for running Python web applications with WSGI-compatible web servers.**

You'll often see:

```python
application = get_wsgi_application()
```

inside the file.

---

# 16. `asgi.py`

ASGI stands for:

> **Asynchronous Server Gateway Interface**

It is a newer interface designed to support asynchronous Python web applications and broader communication patterns.

Django provides an ASGI application through:

```text
asgi.py
```

You'll see something conceptually like:

```python
application = get_asgi_application()
```

For now:

```text
WSGI → traditional synchronous Python web deployment

ASGI → supports asynchronous capabilities
```

Don't worry about deployment details yet.

---

# 17. WSGI vs ASGI

This can be a viva question.

| WSGI                                           | ASGI                                           |
| ---------------------------------------------- | ---------------------------------------------- |
| Web Server Gateway Interface                   | Asynchronous Server Gateway Interface          |
| Traditionally synchronous                      | Supports asynchronous applications             |
| Older Python web interface                     | Newer interface                                |
| Suitable for traditional request-response apps | Supports async and broader connection patterns |

### Viva answer

> WSGI is a standard interface for deploying Python web applications, traditionally focused on synchronous request handling, while ASGI extends this model to support asynchronous applications and communication.

# 22. Very Important: Don't Confuse These

### `settings.py`

Configuration.

### `urls.py`

URL routing.

### `views.py`

Application/request logic.

### `models.py`

Database/data representation.

### `templates/`

HTML/presentation.

This gives us:

```text
URL
 ↓
View
 ↓
Model
 ↓
Template
 ↓
Response
```

# 23. How Does Django Know Which Settings to Use?

When you run:

```bash
python manage.py runserver
```

Django needs to know which settings module belongs to your project.

`manage.py` sets the appropriate environment configuration for the project.

The project settings are then loaded.

This is one reason `manage.py` is more than just a random Python file—it is specifically generated for your project.

---

# 24. What Does `manage.py` Actually Contain?

You'll see something roughly like:

```python
import os
import sys

def main():
    os.environ.setdefault(
        'DJANGO_SETTINGS_MODULE',
        'College.settings'
    )

    from django.core.management import execute_from_command_line
    execute_from_command_line(sys.argv)

if __name__ == '__main__':
    main()
```

**Don't memorize this code.**

Understand the important idea:

```text
manage.py
   ↓
Sets Django settings module
   ↓
Loads Django management system
   ↓
Executes the command you typed
```

For example:

```bash
python manage.py runserver
```

The command is passed to Django's management system.

---

# 25. Why Do We Need `DJANGO_SETTINGS_MODULE`?

This environment variable tells Django:

> "Which settings module should I use?"

For our project:

```text
College.settings
```

means:

```text
College/
   ↓
settings.py
```

So conceptually:

```text
DJANGO_SETTINGS_MODULE
          ↓
College.settings
          ↓
settings.py
```

This is a more advanced detail, but knowing it can impress in a viva.

# 27. Viva Tricky Question ⚠️

### Teacher:

> "Where do we write database queries?"

A beginner might say:

> `settings.py`

❌ Not normally.

`settings.py` **configures the database connection**.

Database interaction is typically performed through:

```text
models
   +
Django ORM
```

So:

> `settings.py` tells Django **which database/how to connect**, while models and the ORM are used to **work with the data**.

---

# 28. Another Tricky Question ⚠️

### Teacher:

> "Where do we write HTML?"

The basic answer:

> In templates.

For example:

```text
templates/
   home.html
```

We'll study templates extensively in Unit III.

---

# 29. Another Tricky Question

### Teacher:

> "Does `urls.py` contain the HTML page?"

No.

`urls.py` defines **URL routing**.

It can connect a URL to a view:

```text
URL
 ↓
View
```

The view can then render a template:

```text
View
 ↓
Template
```
