# 1. Project vs App — First Understand This Properly

This is one of the **most frequently asked Django viva questions**.

Suppose we're building:

> **College Management System**

The complete website/application is the **project**.

Inside it, we might have:

```text
College Management System
│
├── Students
├── Teachers
├── Courses
├── Attendance
└── Accounts
```

Each of these can be a Django **app**.

So:

```text
PROJECT
   │
   ├── App 1
   ├── App 2
   ├── App 3
   └── App 4
```

### Easy analogy

Think about a **college**.

The college is the:

> **Project**

Different departments are:

> **Apps**

For example:

```text
College
│
├── CSE Department
├── ECE Department
├── Mechanical Department
└── Civil Department
```

Each department performs a particular function but belongs to the same college.

Similarly:

```text
Django Project
│
├── accounts
├── students
├── courses
└── attendance
```

---

# 2. What is a Django App?

A Django app is a **Python package that provides a specific functionality within a Django project**.

For example:

```text
accounts → user-related functionality
products → product functionality
orders → order functionality
```

A project can contain multiple apps.

An app can also potentially be reusable across different projects.

---

# 3. Why Does Django Use Apps?

Imagine you create a huge application containing:

```text
Users
Products
Orders
Payments
Reviews
Notifications
```

If all code is placed together, the project becomes difficult to maintain.

Instead:

```text
accounts/
products/
orders/
payments/
reviews/
notifications/
```

Each app has a specific responsibility.

This follows an important software engineering idea:

> **Separation of concerns**

Suppose our project is:

```text
College
```

First enter the directory containing `manage.py`:

```bash
cd College
```

Then run:

```bash
python manage.py startapp students
```

This creates an app named:

```text
students
```

# 7. `views.py`

This is one of the most important files.

```text
students/
└── views.py
```

Views contain code that handles requests and returns responses.

For example:

```python
from django.http import HttpResponse

def home(request):
    return HttpResponse("Welcome to Students App")
```

Here:

```text
home()
```

is a view function.

The basic idea is:

```text
Browser
   ↓
Request
   ↓
View
   ↓
Response
   ↓
Browser
```

We'll spend a lot of time on views in **Module 6**.

---

# 8. `models.py`

This file is used to define **models**.

Models represent application data.

Suppose our students app needs student information.

We might eventually write:

```python
from django.db import models

class Student(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField()
```

This model represents student data.

Conceptually:

```text
Student
----------------
id
name
age
```

Django can use this model to interact with the database.

We'll study models in great detail in **Unit V**.

---

# 9. `admin.py`

This file is used to configure/register models with Django's admin interface.

For example, later we might write:

```python
from django.contrib import admin
from .models import Student

admin.site.register(Student)
```

Then the `Student` model can be managed through Django Admin.

Conceptually:

```text
Model
  ↓
admin.py
  ↓
Django Admin
  ↓
Manage Data
```

We'll study this in Unit V.

---

# 10. `apps.py`

This file contains the configuration class for the app.

For example, Django generates something similar to:

```python
from django.apps import AppConfig

class StudentsConfig(AppConfig):
    default_auto_field = 'django.db.models.BigAutoField'
    name = 'students'
```

This tells Django about the app's configuration.

You generally won't need to modify it much at the beginner level.

---

# 11. `tests.py`

This file is intended for tests for your app.

For example:

```python
from django.test import TestCase
```

You can create test cases to verify that your application behaves correctly.

Example concept:

```text
Test:
"Does the home page return HTTP 200?"
```

We'll cover Django testing later.

---

# 12. `migrations/`

You will see:

```text
migrations/
```

This directory stores migration files related to database schema changes.

Initially:

```text
migrations/
└── __init__.py
```

Later, after creating models and running:

```bash
python manage.py makemigrations
```

you may see something like:

```text
migrations/
├── __init__.py
└── 0001_initial.py
```

Migrations are extremely important in Django.

We'll dedicate a full module to them.

---

# 13. `__init__.py` Inside the App

Just like the project package:

```text
students/
└── __init__.py
```

This is related to Python package structure.

You normally don't need to modify it.

---

# 14. Does Creating an App Automatically Activate It?

**No.**

This is a very important point.

You run:

```bash
python manage.py startapp students
```

Django creates the app files.

But you also need to tell the project that the app is installed.

---

# 15. Registering the App

Open:

```text
College/settings.py
```

Find:

```python
INSTALLED_APPS = [
    ...
]
```

Add your app.

You can use:

```python
INSTALLED_APPS = [
    ...
    'students',
]
```

or, commonly:

```python
INSTALLED_APPS = [
    ...
    'students.apps.StudentsConfig',
]
```

The exact generated app configuration class depends on the app name.

For our app:

```text
students
```

Django generates:

```text
StudentsConfig
```

in:

```text
students/apps.py
```

So:

```python
'students.apps.StudentsConfig'
```

tells Django to use that app configuration.

---

# 16. Why Is `INSTALLED_APPS` Important?

It tells Django:

> "These applications are part of my project."

Django uses this information for various framework functionality, including models, migrations, admin integration, and app configuration.

Conceptually:

```text
Project
   ↓
settings.py
   ↓
INSTALLED_APPS
   ↓
students
   ↓
Django knows about students app
```

---

# 17. Common Beginner Mistake

You create:

```bash
python manage.py startapp students
```

Then you create a model:

```python
class Student(models.Model):
    ...
```

Then run:

```bash
python manage.py makemigrations
```

but Django doesn't detect the model as expected.

One common reason is that the app hasn't been added to:

```python
INSTALLED_APPS
```

So always remember:

```text
startapp
   ↓
Create app
   ↓
Add app to INSTALLED_APPS
```

# 24. Project URL vs App URL

Eventually, Django applications commonly have URL configurations at both levels.

For example:

```text
College/urls.py
```

and:

```text
students/urls.py
```

The project-level URLs can include the app's URLs.

Conceptually:

```text
College/urls.py
       ↓
students/urls.py
       ↓
students.views.home
```

We'll build this in **Module 6/7**.

---

# 25. Why Separate `urls.py` for an App?

Django doesn't automatically create `urls.py` when you run `startapp`.

You can create it yourself.

For example:

```text
students/
├── views.py
├── models.py
└── urls.py
```

This helps keep URL patterns belonging to the app organized.

For a large project:

```text
College
│
├── accounts
│   └── urls.py
│
├── students
│   └── urls.py
│
├── courses
│   └── urls.py
│
└── orders
    └── urls.py
```

This is much easier to maintain.

# 27. Project-Level vs App-Level Files

This distinction is useful:

### Project

```text
College/
├── settings.py
├── urls.py
├── asgi.py
└── wsgi.py
```

### App

```text
students/
├── admin.py
├── apps.py
├── models.py
├── tests.py
├── views.py
└── migrations/
```

So don't confuse:

```text
College/urls.py
```

with:

```text
students/urls.py
```

The first is project-level URL configuration.

The second is an app-level URL configuration that you create when needed.

Yes.

Example:

```text
College/
│
├── accounts/
├── students/
├── teachers/
├── courses/
```

# 29. Can an App Be Used in Multiple Projects?

Yes, if designed appropriately.

This is one reason Django's app-based architecture is useful.

For example, a reusable `accounts` app could potentially be used in multiple Django projects.

# 30. Viva Questions — Very Important

### Q1. What is a Django app?

> A Django app is a Python package that provides a specific functionality within a Django project.

---

### Q2. What command creates an app?

```bash
python manage.py startapp app_name
```

---

### Q3. Does `startapp` create a project?

**No.**

It creates an **app inside an existing Django project context**.

---

### Q4. What is the difference between project and app?

> A project is the overall Django application/configuration, while an app is a component that provides a specific functionality within the project.

---

### Q5. What is `views.py`?

> `views.py` contains view functions or classes that handle requests and produce responses.

---

### Q6. What is `models.py`?

> `models.py` is used to define Django models that represent application data and interact with the database through the ORM.

---

### Q7. What is `admin.py`?

> `admin.py` is used to configure the Django admin interface, including registering models with the admin site.

---

### Q8. What is `apps.py`?

> `apps.py` contains the configuration class for the Django app.

---

### Q9. What is `tests.py`?

> `tests.py` is used to define automated tests for the application.

---

### Q10. What is the `migrations` folder?

> It stores migration files that describe changes to the database schema.

### Teacher:

> "I ran `python manage.py startapp students`. Is my app now available to Django?"

Best answer:

> The app files have been created, but the app should be added to `INSTALLED_APPS` in the project's settings so Django recognizes it as an installed application.

# 32. Tricky Viva Question

### Teacher:

> "Where do you write database configuration?"

Don't answer:

> `models.py`

The better answer is:

> Database connection configuration is specified in `settings.py`, while database models and database operations are handled through models and Django's ORM.

# 36. Practical Coding Question

### Question:

Create a view that returns `"Hello World"`.

```python
from django.http import HttpResponse

def hello(request):
    return HttpResponse("Hello World")
```

Notice:

```text
hello
```

is simply the Python function name.

It could be:

```python
def home(request):
```

or:

```python
def welcome(request):
```

The name itself isn't special. What matters is how you connect the view to a URL.

# 37. Important Concept — Function-Based View

Our view:

```python
def home(request):
    return HttpResponse("Hello")
```

is called a:

> **Function-Based View (FBV)**

because the view is implemented as a Python function.

Later you'll encounter:

> **Class-Based Views (CBVs)**

We'll focus on function-based views first because they make Django's fundamentals easier to understand.

# 38. The Django App Lifecycle — Basic Understanding

When you create an app:

```text
startapp
   ↓
App files created
   ↓
Add app to INSTALLED_APPS
   ↓
Create views/models/etc.
   ↓
Connect URLs
   ↓
Run application
```

This is the workflow you'll repeatedly use.
