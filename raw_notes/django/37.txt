# Module 37 — Django Users

Now we move from **Sessions → Users → Login**.

This module is extremely important because Django provides a built-in authentication system, so you usually **don't need to create your own user table or password system from scratch**.

The main things you need to understand are:

```text
User
Authentication
Authorization
request.user
AnonymousUser
is_authenticated
is_staff
is_superuser
password handling
```

---

# 1. What Is a User in Django?

Django provides a built-in **User model** for representing people who interact with your application.

It comes from:

```python
django.contrib.auth.models
```

You can import it using:

```python
from django.contrib.auth.models import User
```

For example:

```python
from django.contrib.auth.models import User

user = User.objects.create_user(
    username="aman",
    password="StrongPassword123"
)
```

---

# 2. Why Does Django Provide a User Model?

Without Django's authentication framework, you would need to build:

```text
User table
      ↓
Registration
      ↓
Password hashing
      ↓
Login
      ↓
Logout
      ↓
Sessions
      ↓
Authentication checks
      ↓
Permissions
```

Django provides most of this infrastructure already.

This is one reason Django is called a **batteries-included framework**.

The main application is:

# 8. Password — VERY IMPORTANT

A common beginner mistake is thinking:

```python
user.password
```

contains the original password.

It does **not** contain the user's original plaintext password.

Django stores a **password hash** rather than the plaintext password.

---

# 9. Never Store Plaintext Passwords

Never do this:

```python
user.password = "123456"
user.save()
```

This is incorrect for normal password handling.

Instead use:

```python
user.set_password("123456")
user.save()
```

Django hashes the password appropriately.

```python
user.set_password(
```

```text

      ↓

      ↓
```

# 13. Checking a Password

Django provides:

```python
user.check_password(
    "password"
)
```

Example:

```python
if user.check_password(
    "StrongPassword123"
):
    print("Correct password")
```

It returns:

```text
True
```

or:

```text
False
```

This is much safer than comparing plaintext passwords manually.

---

# 14. `create_user()` vs `set_password()`

### Create new user

```python
User.objects.create_user(
    username="aman",
    password="StrongPassword123"
)
```

### Existing user

```python
user.set_password(
    "NewPassword123"
)
user.save()
```

Both correctly handle password hashing.

# 15. `is_active`

The field:

```python
user.is_active
```

indicates whether the account is active.

Typically:

```python
is_active = True
```

means the account is active.

If:

```python
user.is_active = False
```

the account is inactive and Django's normal authentication mechanisms generally won't authenticate that user.

---

# 16. `is_staff`

```python
user.is_staff
```

determines whether the user is allowed to access the Django admin site, subject to permissions.

For example:

```python
user.is_staff = True
```

allows admin-site access if the necessary permissions are available.

Important:

> `is_staff` does **not** mean the user automatically has every permission.

---

# 17. `is_superuser`

```python
user.is_superuser
```

indicates a superuser.

A superuser has all permissions by default.

Typical creation:

```bash
python manage.py createsuperuser
```

Then Django asks for credentials interactively.

---

# 18. `is_staff` vs `is_superuser`

This is a very common viva question.

| Property       | Meaning                                       |
| -------------- | --------------------------------------------- |
| `is_active`    | Account is active                             |
| `is_staff`     | Can access admin site, subject to permissions |
| `is_superuser` | Has all permissions by default                |

A useful mental model:

```text
is_staff
   ↓
Admin access

is_superuser
   ↓
All permissions
```

But don't assume:

```text
is_staff = superuser
```

They are different.

---

# 19. `createsuperuser`

Command:

```bash
python manage.py createsuperuser
```

Django asks you for information such as:

```text
Username:
Email address:
Password:
Password (again):
```

The resulting account is a superuser.

# 20. `request.user`

This is one of the most important things in Django authentication.

Inside a view:

```python
request.user
```

represents the user associated with the current request.

Example:

```python
def dashboard(request):

    user = request.user

    return HttpResponse(
        f"Hello {user.username}"
    )
```

---

# 21. Authenticated User

If the user is logged in:

```python
request.user
```

represents that authenticated user.

Conceptually:

```text
Browser
   ↓
Session
   ↓
Django authentication
   ↓
request.user
```

---

# 22. Anonymous User

What if someone is **not logged in**?

Django doesn't simply give:

```python
request.user = None
```

Instead, it generally gives an:

```python
AnonymousUser
```

So:

```python
request.user
```

is still available.

---

# 23. `is_authenticated`

To check whether the current user is authenticated:

```python
request.user.is_authenticated
```

Example:

```python
if request.user.is_authenticated:
    return HttpResponse("Logged in")

return HttpResponse("Not logged in")
```

---

# 24. Important Trap: No Parentheses

This is correct:

```python
request.user.is_authenticated
```

This is incorrect:

```python
request.user.is_authenticated()
```

`is_authenticated` is an attribute/property-like boolean check, not a method you call.

---

# 25. `is_anonymous`

You may also encounter:

```python
request.user.is_anonymous
```

For a logged-out user, this is generally `True`.

For an authenticated user:

```python
request.user.is_anonymous
```

is generally `False`.

Usually, prefer:

```python
request.user.is_authenticated
```

when your question is:

> "Is the user logged in?"

---

# 26. Authentication vs Authorization

This distinction is extremely important.

### Authentication

> Who are you?

Example:

```text
Username + Password
        ↓
Identity verification
```

### Authorization

> What are you allowed to do?

Example:

```text
Can this user delete students?
Can this user access admin?
Can this user edit products?
```

Remember:

```text
Authentication = WHO
Authorization = WHAT
```

---

# 27. Example

Suppose:

```text
Aman logs in
```

Authentication asks:

```text
Is this really Aman?
```

After authentication:

```text
request.user = Aman
```

Authorization asks:

```text
Can Aman delete Student #10?
```

These are two different questions.

# 44. Why Does `request.user` Work?

Django authentication middleware works together with the session system.

A simplified flow is:

```text
Request
   ↓
SessionMiddleware
   ↓
AuthenticationMiddleware
   ↓
request.user
   ↓
View
```

So when your view runs, Django has already associated the request with an authenticated or anonymous user.

---

# 45. Middleware Connection

You normally see:

```python
MIDDLEWARE = [
    ...
    "django.contrib.sessions.middleware.SessionMiddleware",
    ...
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    ...
]
```

### SessionMiddleware

Provides access to:

```python
request.session
```

### AuthenticationMiddleware

Provides:

```python
request.user
```

This relationship is worth remembering.

# 48. Important Security Rule

Never write your own password hashing system when Django's authentication system can handle it.

Don't do:

```python
password == stored_password
```

for raw plaintext passwords.

Use Django's authentication APIs.

For password creation/change:

```python
user.set_password(...)
```

For password checking:

```python
user.check_password(...)
```

For authentication:

```python
authenticate(...)
```

We'll learn `authenticate()` in the next module.

# 49. Custom User Model — Advanced Viva Point

Django allows you to create a **custom user model**.

Instead of:

```python
django.contrib.auth.models.User
```

a project can define its own user model.

This is useful when you need things like:

```text
email as login identifier
additional user fields
different authentication requirements
```

A common approach is extending/customizing Django's authentication model using `AbstractUser` or `AbstractBaseUser`.

This is an advanced topic, but remember:

> If you know from the beginning that your application needs a custom user model, it's generally best to configure it at the start of the project rather than switching later.

For this syllabus, the built-in `User` model is sufficient unless your project specifically requires customization.

---

# 50. `AUTH_USER_MODEL`

Django uses:

```python
AUTH_USER_MODEL
```

to specify the project's user model.

For the default user model, Django uses its built-in authentication model.

In a custom-user project, you might see:

```python
AUTH_USER_MODEL = "accounts.User"
```

Meaning:

```text
accounts app
      ↓
User model
      ↓
Project's user model
```

---

# 51. Why Custom User Models Matter

Suppose your application wants:

```text
email = login identifier
```

instead of:

```text
username = login identifier
```

A custom user model may be appropriate.

But don't create a custom user model just because you can.

Use the built-in model when it satisfies the requirements.
