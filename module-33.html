Module 33 — Django Users, Groups & Permissions

This module is extremely important because it explains who can access your Django application and what they are allowed to do.

You already learned Django Admin. Now we'll understand the system behind it:

TEXT
Authentication → Who are you?
Authorization  → What are you allowed to do?

By the end, you should be able to answer common viva questions and write permission-based Django code.

1. Authentication vs Authorization

This is the first thing to memorize.

Authentication

Authentication answers:

Who are you?

Example:

TEXT
Username: Aman
Password: ********

Django checks whether the credentials are valid.

Authorization

Authorization answers:

What are you allowed to do?

For example:

TEXT
Aman
    ↓
Can view students
Can add students
Cannot delete students

Memorize:

TEXT
Authentication → Identity
Authorization  → Permissions

2. Django User System

Django provides a built-in authentication framework.

It includes functionality for:

  • Users

  • Sessions
  • Login/logout
  • Groups
  • Permissions
  • Authentication helpers
  • Password hashing
  • Admin integration

The main model is:

PYTHON
User

Django provides it through:

PYTHON
django.contrib.auth

3. Importing User

A common way to import Django's default User model is:

PYTHON
from django.contrib.auth.models import User

Then you can work with it using the ORM.

For example:

PYTHON
User.objects.all()

5. Never Store Passwords as Plain Text

This is very important.

You should never do:

PYTHON
user.password = "123456"

as your normal password-setting approach.

Instead use:

PYTHON
user.set_password("123456")

Django hashes the password.

6. Creating a User

You can create a regular user:

PYTHON
from django.contrib.auth.models import User

user = User.objects.create_user(
    username="aman",
    password="StrongPassword123"
)

This is the preferred approach.

Django handles password hashing.

7. Creating a Superuser

You can use:

BASH
python manage.py createsuperuser

Django asks for:

TEXT
Username
Email
Password

The resulting user has superuser privileges.

8. is_active

A user has:

PYTHON
user.is_active

Normally:

PYTHON
True

An inactive user is generally prevented from authenticating normally.

Example:

PYTHON
user.is_active = False
user.save()

This can effectively disable the user's account without deleting the user record.

9. is_staff

PYTHON
user.is_staff

determines whether the user is allowed to access the Django Admin site, subject to the admin's authentication/permission checks.

Example:

PYTHON
user.is_staff = True
user.save()

But remember:

is_staff=True does not mean the user has every permission.

10. is_superuser

PYTHON
user.is_superuser

A superuser has all permissions by default.

For example:

TEXT
is_superuser = True

means Django treats the user as having all permissions without requiring each individual permission to be assigned.

11. Staff vs Superuser

Very common viva question.

Property Meaning
is_active Account is active
is_staff Can access admin site
is_superuser Has all permissions

Think:

TEXT

    ↓

    ↓
Can access admin?

is_superuser
    ↓

A staff user can have limited permissions.

A superuser has all permissions by default.

14. Permission Object

Django stores permissions as permission records.

You can access them through:

PYTHON
from django.contrib.auth.models import Permission

For example:

PYTHON
Permission.objects.all()

You generally don't manually create the standard CRUD permissions because Django creates them as part of its model permission system.

15. Checking a Permission

Suppose:

PYTHON
user

is a User object.

You can check:

PYTHON
user.has_perm("students.view_student")

This returns:

PYTHON
True

or:

PYTHON
False

The format is:

TEXT
app_label.permission_codename

So:

TEXT
students.view_student

means:

TEXT
App: students
Permission: view_student

16. Permission Naming

For a model called:

PYTHON
Student

Django's standard permission codenames are generally:

TEXT
add_student
change_student
delete_student
view_student

Therefore:

PYTHON
user.has_perm("students.add_student")

checks whether the user can add students.

19. Groups

Suppose you have 100 teachers.

You don't want to individually assign the same permissions to every teacher.

Instead create a group:

TEXT
Teachers

and assign permissions to the group.

Then add users to the group.

20. Group Concept

Think:

TEXT
Group
  ↓
Permissions
  ↓
Users

Example:

TEXT
Teachers
   ├── view_student
   ├── add_student
   └── change_student

Then:

TEXT
Aman
Rahul
Priya

are members of the Teachers group.

They inherit the group's permissions.

21. Creating a Group

You can use Django Admin, or programmatically:

PYTHON
from django.contrib.auth.models import Group

teachers = Group.objects.create(
    name="Teachers"
)

Then assign permissions.

22. Adding a Permission to a Group

Suppose we retrieve a permission:

PYTHON
from django.contrib.auth.models import Permission

permission = Permission.objects.get(
    codename="view_student"
)

Then:

PYTHON
teachers.permissions.add(
    permission
)

Now the group has that permission.

23. Adding a User to a Group

Suppose:

PYTHON
user = User.objects.get(
    username="aman"
)

Then:

PYTHON
user.groups.add(
    teachers
)

Now Aman belongs to the Teachers group.

24. Removing a User From a Group

PYTHON
user.groups.remove(
    teachers
)

25. Check User's Groups

PYTHON
user.groups.all()

This returns the groups the user belongs to.

27. user_permissions

Django User has a relationship for permissions assigned directly to that user.

Conceptually:

PYTHON
user.user_permissions.all()

This gives directly assigned permissions.

While:

PYTHON
user.groups.all()

gives their groups.

28. Checking Permissions From Groups

Suppose:

TEXT

    ↓

TEXT

Then:

PYTHON
user.has_perm(
    "students.view_student"
)

can return:

PYTHON

because the permission is inherited through the group.

29. Custom Permissions

Django can also define permissions beyond the standard four.

In a model:

PYTHON
class Student(models.Model):
    name = models.CharField(max_length=100)

    class Meta:
        permissions = [
            (
                "can_publish_student",
                "Can publish student"
            ),
        ]

Now you have a custom permission.

30. Why Custom Permissions?

Suppose your application has a blog.

Standard permissions:

TEXT

or:

TEXT

or:

TEXT

Custom permissions allow application-specific authorization rules.

34. is_authenticated

You can check:

PYTHON
if request.user.is_authenticated:
    ...

Meaning:

Is the current request associated with an authenticated user?

Example:

PYTHON
def profile(request):

    if request.user.is_authenticated:
        return HttpResponse(
            f"Hello {request.user.username}"
        )

    return HttpResponse(
        "Please log in."
    )

35. Important: is_authenticated Is Not a Function

This is a common beginner mistake.

Correct:

PYTHON
request.user.is_authenticated

Not:

PYTHON
request.user.is_authenticated()

It's a property-like attribute.

36. Protecting a View

Suppose you want only logged-in users to access:

TEXT
/profile/

You can use:

PYTHON
from django.contrib.auth.decorators import login_required


@login_required
def profile(request):
    return HttpResponse(
        "Welcome to your profile"
    )

37. What Does login_required Do?

If the user is authenticated:

TEXT
View executes

If the user isn't authenticated:

TEXT
Redirect to login page

Conceptually:

TEXT
/profile/
    ↓
Authenticated?
   / \
 Yes  No
 ↓     ↓
View  Login

38. Setting the Login URL

You can configure:

PYTHON
LOGIN_URL = "/login/"

in settings.py.

Then:

PYTHON
@login_required
def profile(request):
    ...

will redirect unauthenticated users to the configured login URL.

39. Login URL With next

Django commonly preserves the original destination using a next query parameter.

For example:

TEXT
/login/?next=/profile/

After successful authentication, your login flow can use that destination to send the user back to the page they originally requested.

This is an important authentication concept.

40. Permission-Based View Protection

login_required checks:

Is the user logged in?

It does not check whether they have a particular permission.

For permissions, you can use:

PYTHON
from django.contrib.auth.decorators import permission_required


@permission_required(
    "students.change_student"
)
def edit_student(request, id):
    ...

Now Django checks the required permission.

41. permission_required

General syntax:

PYTHON
@permission_required(
    "app_label.permission_codename"
)
def my_view(request):
    ...

Example:

PYTHON
@permission_required(
    "students.delete_student"
)
def delete_student(request, id):
    ...

42. permission_required and Login

By default, permission checks work together with Django authentication.

For a user who isn't authenticated, Django can redirect them to the login page according to the decorator's configuration.

If an authenticated user lacks the permission, access is denied.

43. raise_exception=True

You can configure the decorator:

PYTHON
@permission_required(
    "students.delete_student",
    raise_exception=True
)
def delete_student(request, id):
    ...

Now if the authenticated user doesn't have the permission, Django raises a permission-denied condition rather than redirecting them to the login page.

This generally results in a 403 Forbidden response.

44. login_required vs permission_required

Very important:

login_required

PYTHON
@login_required

asks:

Is the user authenticated?

permission_required

PYTHON
@permission_required(
    "students.change_student"
)

asks:

Does the user have this specific permission?

46. Checking Staff Status

You can also manually check:

PYTHON
if request.user.is_staff:
    ...

Example:

PYTHON
def admin_area(request):

    if not request.user.is_staff:
        return HttpResponseForbidden(
            "Staff only"
        )

    return HttpResponse(
        "Welcome staff member"
    )

But for specific permissions, permission checks are usually more precise than simply checking is_staff.

47. Checking Superuser

PYTHON
if request.user.is_superuser:
    ...

This checks whether the user is a superuser.

Again, don't use superuser status as a substitute for every authorization rule in a normal application. Specific permissions are usually better when you want least-privilege access.

48. Template Permission Checks

You can also check permissions in templates.

Example:

HTML
{% if perms.students.add_student %}
    <a href="{% url 'student_create' %}">
        Add Student
    </a>
{% endif %}

This means:

Show the Add Student link if the current user has that permission.

49. Important Security Point

Hiding a button is not security.

For example:

HTML
{% if perms.students.delete_student %}
    <button>Delete</button>
{% endif %}

only controls whether the button is displayed.

A malicious user could still manually send a request.

Therefore the view/server must also enforce authorization.

Think:

TEXT
Template check
      +
Server-side permission check

The server-side check is essential.

50. Permission Check in a View

Example:

PYTHON
from django.contrib.auth.decorators import permission_required


@permission_required(
    "students.delete_student",
    raise_exception=True
)
def delete_student(request, id):

    student = get_object_or_404(
        Student,
        id=id
    )

    student.delete()

    return redirect("student_list")

Now deletion is protected by a permission.

58. Viva Masterclass

Q1. What is authentication?

Authentication is the process of verifying the identity of a user.

Q2. What is authorization?

Authorization determines what an authenticated user is allowed to access or perform.

Q3. What is Django's built-in User model?

It is the default user model provided by Django's authentication framework for managing users and authentication-related information.

Q4. What is is_staff?

It indicates whether a user is allowed to access the Django Admin site, subject to the relevant access checks and permissions.

Q5. What is is_superuser?

It indicates that the user has all permissions by default.

Q6. What is is_active?

It indicates whether the user account is active.

Q7. What are Django's default model permissions?

Add, change, delete, and view.

Q8. What is a Group?

A group is a collection of users to which permissions can be assigned collectively.

Q9. Why use groups?

Groups simplify permission management when multiple users need the same set of permissions.

Q10. How do you check a permission?

PYTHON
user.has_perm(
    "students.view_student"
)

Q11. What does login_required do?

It restricts a view to authenticated users and redirects unauthenticated users to the login flow.

Q12. What does permission_required do?

It restricts a view based on a specified Django permission.

Q13. Difference between is_staff and is_superuser?

is_staff allows admin access, while is_superuser gives all permissions by default.

Q14. Can a staff user have limited permissions?

Yes. Staff status does not automatically mean the user has every model permission.

Q15. Why isn't hiding a delete button enough?

Because client-side/template visibility is not an authorization mechanism. The server-side view must enforce the permission.

59. One Very Important Interview Scenario

Interviewer:

"I have 100 teachers. All teachers should be able to view and edit students, but not delete them. How would you implement this?"

A strong answer:

"I would create a Teachers group, assign the view_student and change_student permissions to that group, and add all teacher users to it. I would not assign the delete_student permission. The relevant views would also enforce permissions using Django's authorization mechanisms."

60. Another Interview Scenario

Question:

"What is the difference between login_required and permission_required?"

Answer:

"login_required checks whether the user is authenticated, while permission_required checks whether the user has a specific permission. A user can be authenticated but still lack the permission required for an operation."

Excellent viva answer.
