MODULE 1 — Growth, History of Blockchain & Bitcoin

This module is very important for theory because it can easily become a 5-mark or 10-mark question.

Your PPT specifically presents blockchain's history as an evolution of several earlier ideas, culminating in Bitcoin in 2008 and its practical implementation in 2009.

1. First understand the BIG picture

Don't memorize the history as random years.

Think of it as a sequence of problems → attempted solutions → Bitcoin.

Digital money
     ↓
How to make digital cash secure?
     ↓
How to provide anonymity?
     ↓
How to prevent double spending?
     ↓
How to remove dependence on a central authority?
     ↓
How can many computers agree on one ledger?
     ↓
Bitcoin + Blockchain

The key problem that earlier approaches struggled to solve completely was double spending in a trustless/permissionless environment. Bitcoin's blockchain addressed this using an ordered chain of transaction blocks secured by Proof of Work.

2. What is Blockchain?

Before studying its history, know the definition.

Simple definition

A blockchain is a shared digital record-keeping system in which copies of the records are maintained by participants of the network.

Technical definition

Your PPT defines blockchain as a:

Peer-to-peer, distributed ledger that is cryptographically secure, append-only, immutable, and updateable through consensus among peers.

Let's understand every word.

Peer-to-peer

There is no requirement for one central server to control the entire network.

Traditional:

        Central Server
        /     |      \
      A       B       C


Blockchain:

    A -------- B
    | \        |
    |  \       |
    C -------- D
     \         /
        E

Participants communicate with one another.

Distributed ledger

The ledger is distributed among participating nodes.

Instead of:

          CENTRAL DATABASE
          /      |       \
        User1  User2    User3

we have:

Node A → Copy of ledger
Node B → Copy of ledger
Node C → Copy of ledger
Node D → Copy of ledger

Cryptographically secure

Cryptography provides important security properties such as:

  • Integrity
  • Data-origin authentication
  • Non-repudiation

Your PPT specifically connects blockchain security with public-key cryptography, digital signatures and cryptographic hash functions.

Append-only

New records are added to the ledger rather than simply overwriting previous records.

Immutable

Once data is sufficiently confirmed and incorporated into the chain, changing historical data becomes extremely difficult.

Exam wording:

Immutability means that previously recorded blockchain data is extremely difficult to alter without being detected or violating the consensus/security assumptions of the network.

Consensus-based

A new state/update is accepted according to the blockchain's consensus mechanism.

Your PPT explicitly states that updates are validated according to protocol rules and added after consensus is reached.

3. Why did we need Blockchain?

This is one of the most important conceptual questions.

Suppose I want to send ₹100 digitally to you.

With a traditional system:

A → Bank → Database → Bank → B

The bank maintains the authoritative record.

But suppose we want:

A → B

without depending on a central authority.

Now we face a major problem.

Double Spending Problem

Digital information can be copied.

Suppose I have:

₹100 digital token

I send the same digital token to:

You       → ₹100
Someone else → ₹100

If the system cannot determine which transaction happened first, I have effectively spent the same ₹100 twice.

That is the double-spending problem.

Your PPT explains that digital data can easily be copied, making double spending a fundamental problem for digital currencies.

Exam definition

Double spending is the problem in a digital currency system where the same digital asset can be spent more than once because digital information can be copied.

⭐ Remember this definition.

4. Electronic Cash

Before Bitcoin, researchers had already been working on digital/electronic cash.

Your PPT states that electronic-cash protocols existed since the 1980s, based on a model proposed by David Chaum.

Two important requirements were:

1. Accountability

The system should ensure:

  • money is spent only once
  • money can be spent by its rightful owner

2. Anonymity

The system should protect the user's identity/privacy.

David Chaum used cryptographic concepts including:

  • Blind signatures
  • Secret sharing

5. What is a Blind Signature?

You don't need to go extremely deep into it in this module.

Basic idea:

Normally:

Signer → sees document → signs document

With a blind signature:

Signer → signs without seeing the actual contents

Your PPT describes blind signatures as allowing a document to be signed without actually seeing it.

This helped electronic cash achieve privacy.

10. Bitcoin and State Machine Replication

This is a slightly advanced point that can make your 10-mark answer stronger.

A distributed system needs participating nodes to eventually agree on the same state.

This is related to State Machine Replication (SMR).

You don't need to go deeply into SMR yet because we will cover distributed systems and consensus in later modules.

Just remember:

Bitcoin doesn't just create digital currency; it also provides a way for distributed nodes to converge on a consistent ledger state.

12. Cryptocurrency vs Blockchain

This is a common confusion.

Cryptocurrency

A digital currency secured using cryptography. Your PPT gives this definition.

Examples:

  • Bitcoin
  • Ether

Blockchain

The underlying distributed ledger technology used to record and validate transactions.

Therefore:

Blockchain ≠ Bitcoin

Rather:

Bitcoin
   ↓
Uses blockchain technology

Easy analogy

Think:

Internet → infrastructure
Website → application

Blockchain → infrastructure
Bitcoin → application/currency

This analogy is only for understanding; in an exam, use the technical definitions.

1. Why Do We Need Consensus?

Let's start from the fundamental problem.

Suppose there are 5 blockchain nodes:

       N1
      /  \
    N2    N3
     \    /

      N5

        ↓

        ↓

But these nodes:

  • May receive messages at different times.
  • May fail.
  • May be malicious.
  • May receive conflicting transactions.

Therefore, simply saying:

"Everyone, please agree"

1. What is Cryptography?

Cryptography is the study and application of techniques used to protect information by transforming it so that unauthorized parties cannot understand or modify it.

The basic objective is to provide security services such as:

Confidentiality

Information should be available only to authorized entities.

Integrity

Information should only be modified by authorized entities.

Authentication

Provides assurance about the identity of an entity or the validity/source of a message.

Non-repudiation

An entity should not be able to deny a previous action when there is sufficient evidence.

Accountability

Actions affecting security can be traced back to the responsible party.

7. RSA Key Generation — Basic Steps ⭐⭐⭐⭐⭐

The standard conceptual procedure is:

Step 1 — Choose two large primes

$$p,\ q$$

Step 2 — Calculate

$$n=pq$$

Step 3 — Calculate Euler's totient

$$\phi(n)=(p-1)(q-1)$$

Step 4 — Choose public exponent

Choose \(e\) such that:

$$gcd(e,\phi(n))=1$$

Step 5 — Calculate private exponent

Find \(d\) such that:

$$ed\equiv1\pmod{\phi(n)}$$

Public key

$$(e,n)$$

Private key

$$(d,n)$$

8. RSA Encryption and Decryption ⭐⭐⭐⭐⭐

For message \(M\):

Encryption

$$C=M^e\bmod n$$

Decryption

$$M=C^d\bmod n$$

So remember:

PUBLIC KEY  → encryption
PRIVATE KEY → decryption

for the confidentiality use case.

and:

$$\phi(n)=(3-1)(11-1)=20$$

Choose:

$$e=3$$

because:

$$gcd(3,20)=1$$

Now find \(d\):

$$3d\equiv1\pmod{20}$$

Therefore:

$$d=7$$

because:

$$3\times7=21\equiv1\pmod{20}$$

So:

Public key  = (3,33)

This is just a toy example; real RSA uses extremely large numbers.

22. Security Requirements of a Cryptographic Hash ⭐⭐⭐⭐⭐

This is a very likely 5-mark question.

Three important resistance properties are:

1. Preimage resistance

Given:

$$h$$

it should be computationally difficult to find:

$$M$$

such that:

$$H(M)=h$$

In simple words:

Given a hash, it should be difficult to find the original input.

23. Second-Preimage Resistance

Given:

Message M1
Hash H(M1)

it should be difficult to find a different message \(M_2\) such that:

$$H(M_1)=H(M_2)$$

So:

Given one specific message, it should be difficult to find another message having the same hash.

24. Collision Resistance ⭐⭐⭐⭐⭐

A collision occurs when:

$$M_1\neq M_2$$

but:

$$H(M_1)=H(M_2)$$

Example:

Message A ──→ HASH ──→ ABC123

Message B ──→ HASH ──→ ABC123

That's a collision.

A secure hash function should make finding such a pair computationally difficult.

Your book explicitly lists collision resistance, preimage resistance and second-preimage resistance among the key hash-function security properties.
