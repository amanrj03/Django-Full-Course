Module 24 — POST Redirect Pattern (PRG)

This module is short but very important in practical Django development and viva.

The main concept is:

After successfully processing a POST request, redirect the user to another page instead of directly rendering the response.

This pattern is called:

POST → Redirect → GET (PRG)

1. The Problem With Directly Rendering After POST

Suppose we have a student registration form.

User submits:

TEXT
Name: Aman
Age: 21

Browser sends:

TEXT
POST /students/register/

Your Django view processes the data:

PYTHON
if request.method == "POST":
    form = StudentForm(request.POST)

    if form.is_valid():
        # Save/process data

Now suppose you do:

PYTHON
return render(request, "success.html")

The browser is currently displaying the response to the POST request.

If the user presses:

TEXT
F5 / Refresh

the browser may ask:

"Resubmit the form?"

Because the current page came from a POST request.

This can potentially cause the same operation to happen again.

For example:

TEXT
POST
↓
Create student
↓
Success page
↓
Refresh
↓
POST again
↓
Create student again

That could result in duplicate data.

2. The Solution: Redirect

Instead of:

PYTHON
return render(request, "success.html")

use:

PYTHON
return redirect("success")

Now the flow becomes:

TEXT
POST
 ↓
Process data
 ↓
Redirect
 ↓
GET
 ↓
Success page

This is:

POST → Redirect → GET

3. Why Is This Called PRG?

PRG stands for:

TEXT
P → POST
R → Redirect
G → GET

So:

TEXT
POST request
      ↓
Process submitted data
      ↓
HTTP Redirect
      ↓
GET request
      ↓
Display result

The browser's final page is now the result of a GET request.

Therefore, refreshing the page normally repeats the GET rather than resubmitting the original POST.

4. Basic Django Example

PYTHON
from django.shortcuts import render, redirect


def student_form(request):

    if request.method == "POST":

        form = StudentForm(request.POST)

        if form.is_valid():

            # Process data

            return redirect("success")

    else:
        form = StudentForm()

    return render(
        request,
        "student_form.html",
        {"form": form}
    )

The important line is:

PYTHON
return redirect("success")

5. Where Does "success" Come From?

Usually from a named URL.

For example:

PYTHON
path(
    "success/",
    views.success,
    name="success"
)

Then:

PYTHON
return redirect("success")

Django finds the URL whose name is:

TEXT
success

and redirects the browser there.

6. The Success View

PYTHON
def success(request):
    return render(
        request,
        "success.html"
    )

Complete flow:

TEXT
POST /students/register/
             ↓
       student_form()
             ↓
        form.is_valid()
             ↓
           valid
             ↓
    redirect("success")
             ↓
GET /students/success/
             ↓
        success()
             ↓
       success.html

7. redirect() vs render()

This is a common viva question.

render()

PYTHON
return render(
    request,
    "success.html"
)

renders a template directly.

Conceptually:

TEXT
View
 ↓
Template
 ↓
HTTP response

redirect()

PYTHON
return redirect("success")

tells the browser to go to another URL.

Conceptually:

TEXT
View
 ↓
Redirect response
 ↓
Browser makes GET request
 ↓
New view

8. Important Difference

render() redirect()
Renders a template Sends browser to another URL
Usually returns the page directly Causes a new request
Doesn't change the browser URL to another route by itself Browser URL changes
Useful for displaying a page Useful after successful POST/action

9. Why Not Just Render the Success Page?

Consider:

PYTHON
if form.is_valid():

    form.save()

    return render(
        request,
        "success.html"
    )

The browser's current request is still:

TEXT
POST

Then refresh can potentially repeat the POST.

Better:

PYTHON
if form.is_valid():

    form.save()

    return redirect("success")

Now:

TEXT
POST
 ↓
save
 ↓
redirect
 ↓
GET
 ↓
success page

10. PRG Is Especially Useful for Database Operations

Suppose:

PYTHON
Student.objects.create(
    name="Aman"
)

If the POST gets accidentally repeated, you could create another student.

Similarly:

TEXT
POST /create-order/
POST /payment/
POST /register/
POST /comment/
POST /contact/

are actions where duplicate submissions can be problematic.

PRG is therefore widely used after successful form submissions.

11. Redirect With URL Name

Recommended:

PYTHON
return redirect("success")

with:

PYTHON
path(
    "success/",
    views.success,
    name="success"
)

This is better than hardcoding the URL:

PYTHON
return redirect("/students/success/")

Why?

Because if the URL changes later:

PYTHON
path(
    "registration-complete/",
    views.success,
    name="success"
)

your Python code can still use:

PYTHON
redirect("success")

12. Redirect to Another View

You can also redirect using a view name:

PYTHON
return redirect("home")

provided that:

PYTHON
path(
    "",
    views.home,
    name="home"
)

exists.

13. Redirect With Parameters

Suppose your URL is:

PYTHON
path(
    "student/<int:id>/",
    views.student_detail,
    name="student_detail"
)

You can redirect with the parameter:

PYTHON
return redirect(
    "student_detail",
    id=10
)

Django resolves it to something like:

TEXT
/student/10/

This is similar to URL reversing.

14. Redirect Using reverse()

You can also do:

PYTHON
from django.urls import reverse
from django.shortcuts import redirect

Then:

PYTHON
return redirect(
    reverse("success")
)

But normally:

PYTHON
return redirect("success")

is simpler.

Django's redirect() can resolve a named URL for you.

15. PRG With a Django Form

Let's combine what we've learned.

forms.py

PYTHON
from django import forms


class StudentForm(forms.Form):

    name = forms.CharField(
        min_length=3
    )

    age = forms.IntegerField(
        min_value=18,
        max_value=60
    )

views.py

PYTHON
from django.shortcuts import render, redirect
from .forms import StudentForm


def student_form(request):

    if request.method == "POST":

        form = StudentForm(request.POST)

        if form.is_valid():

            name = form.cleaned_data["name"]
            age = form.cleaned_data["age"]

            # Process/save data here

            return redirect("success")

    else:

        form = StudentForm()

    return render(
        request,
        "student_form.html",
        {"form": form}
    )

        request,
        "success.html"

16. What Happens When Form Is Invalid?

This is very important.

Suppose user submits:

TEXT
Name: A
Age: 12

Validation fails.

The view does:

PYTHON
if form.is_valid():
    return redirect("success")

Since:

PYTHON
form.is_valid()

is False, Django does not redirect.

It reaches:

PYTHON
return render(
    request,
    "student_form.html",
    {"form": form}
)

The form is displayed again with errors.

So the complete behavior is:

TEXT
POST
 ↓
Validation
 ↓
 ┌─────────────┐
 │             │
Valid        Invalid
 │             │
 ↓             ↓
Redirect     Render form
 │             +
 ↓           errors
GET
 ↓
Success

This is the standard pattern.

17. Why Don't We Redirect When Validation Fails?

Because we want to preserve the submitted form and its errors.

Suppose:

TEXT
Age = 15

and minimum age is 18.

We want the user to see:

TEXT
Age
15

❌ Ensure this value is greater than or equal to 18.

If we redirected immediately, we'd need another mechanism to preserve the errors/data.

So the usual pattern is:

TEXT
Invalid POST → render form with errors
Valid POST → redirect

19. POST Redirect vs Redirect After Every POST

Not every POST necessarily has to use PRG.

The important principle is:

After a successful state-changing POST, redirecting is generally a good practice when the next page represents the result of that operation.

For example:

TEXT
Create student → redirect to student detail
Update student → redirect to student detail
Delete student → redirect to student list
Submit registration → redirect to success/dashboard

20. Redirect After Create

Example:

PYTHON
def create_student(request):

    if request.method == "POST":

        form = StudentForm(request.POST)

        if form.is_valid():

            student = Student.objects.create(
                name=form.cleaned_data["name"]
            )

            return redirect(
                "student_detail",
                id=student.id
            )

    else:
        form = StudentForm()

    return render(
        request,
        "create_student.html",
        {"form": form}
    )

Flow:

TEXT
POST
 ↓
Create student
 ↓
Redirect to student detail
 ↓
GET student detail

21. Redirect After Delete

Example:

PYTHON
def delete_student(request, id):

    if request.method == "POST":

        student = get_object_or_404(
            Student,
            id=id
        )

        student.delete()

        return redirect("student_list")

Flow:

TEXT
POST /student/10/delete/
          ↓
      Delete student
          ↓
redirect("student_list")
          ↓
GET /students/

This is a very common Django pattern.

22. HTTP Redirect Status

A redirect is represented by an HTTP 3xx response.

For example:

TEXT
302 Found

is commonly used for redirects.

Django's:

PYTHON
redirect()

creates an appropriate redirect response.

You generally don't need to manually construct the HTTP response for ordinary redirects.

23. Common Mistake: Calling render() Instead of redirect()

Bad after successful POST:

PYTHON
if form.is_valid():

    form.save()

    return render(
        request,
        "success.html"
    )

Better:

PYTHON
if form.is_valid():

    form.save()

    return redirect("success")

24. Common Mistake: Redirect Before Processing

Wrong:

PYTHON
if request.method == "POST":

    return redirect("success")

    form.save()

Why?

Because:

PYTHON
return

immediately exits the function.

Therefore this:

PYTHON
form.save()

will never execute.

Correct:

PYTHON
if form.is_valid():

    form.save()

    return redirect("success")

25. Common Mistake: No Named URL

If you write:

PYTHON
return redirect("success")

but don't have:

PYTHON
name="success"

Django may raise:

TEXT
NoReverseMatch

So make sure:

PYTHON
path(
    "success/",
    views.success,
    name="success"
)

exists.

26. redirect() vs reverse()

This is a useful viva distinction.

reverse()

Builds a URL string.

PYTHON
reverse("success")

might produce:

TEXT
/success/

redirect()

Returns an HTTP redirect response.

PYTHON
redirect("success")

tells the browser to navigate to that URL.

Simple rule:

TEXT
reverse()  → creates URL
redirect() → redirects browser

27. Viva Questions

Q1. What is PRG?

PRG stands for Post-Redirect-Get. It is a web design pattern where a successful POST request is followed by a redirect, and the browser then makes a GET request to display the result.

Q2. Why is PRG used?

It prevents the final page from being directly associated with the POST submission, reducing accidental duplicate submissions when the user refreshes the page.

Q3. What function is used for redirecting in Django?

PYTHON
redirect()

Q4. Difference between render() and redirect()?

render() generates a response using a template, while redirect() sends a redirect response causing the browser to make a new request to another URL.

Q5. What happens when validation fails?

The form is normally rendered again with its validation errors rather than redirecting to the success page.

Q6. Why use named URLs with redirect()?

Named URLs avoid hardcoding URL paths and make the application easier to maintain when URL patterns change.

Q7. Can redirect() accept URL parameters?

Yes.

PYTHON
return redirect(
    "student_detail",
    id=10
)

Q8. What happens when the user refreshes after PRG?

The browser refreshes the final GET request instead of normally resubmitting the original POST.

28. Exam Question

"Explain POST-Redirect-GET pattern in Django."

A good answer:

POST-Redirect-GET (PRG) is a web design pattern used after successful form submission. First, the client sends a POST request containing form data. Django validates and processes the data. Instead of directly rendering the success page for the POST request, Django returns a redirect using redirect(). The browser then sends a new GET request to the redirected URL. This prevents the success page from being directly associated with the POST request and helps avoid accidental duplicate form submissions when the page is refreshed.
