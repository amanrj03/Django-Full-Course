Module 34 — Database Configuration & Connection

Now we move from working with models and ORM to understanding how Django actually connects to a database.

This is important because Django does not store your application's data itself. It uses a database such as:

  • SQLite
  • MySQL
  • PostgreSQL
  • MariaDB
  • Oracle

Django's ORM provides a common Python interface over these databases.

1. The Big Picture

Remember:

TEXT
Django Application
       ↓
     Models
       ↓
      ORM
       ↓
Database Backend
       ↓
   Database

For example:

TEXT
Student.objects.all()
       ↓
      ORM
       ↓
SQL generated by Django
       ↓
    SQLite

or:

TEXT
Student.objects.all()
       ↓
      ORM
       ↓
    PostgreSQL

Your Python ORM code can remain mostly the same even when the database backend changes.

2. Where Is Database Configuration?

Database configuration is normally inside:

TEXT
settings.py

Specifically:

PYTHON
DATABASES = {
    ...
}

3. Default Django Database

When you create a new Django project, Django commonly configures:

PYTHON
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
    }
}

This means:

TEXT
Database backend → SQLite
Database file   → db.sqlite3

4. What Is SQLite?

SQLite is a lightweight relational database that stores the database in a file.

For example:

TEXT
College/
├── manage.py
├── db.sqlite3
└── students/

The file:

TEXT
db.sqlite3

contains your database.

5. Why Does Django Use SQLite by Default?

SQLite is convenient because:

  • No separate database server is required
  • Very easy to set up
  • Comes as a file
  • Good for development
  • Good for learning
  • Good for small applications

You don't have to install MySQL or PostgreSQL just to start learning Django.

6. SQLite vs Server Database

SQLite

TEXT
Django
  ↓
db.sqlite3

PostgreSQL

TEXT
Django
  ↓
PostgreSQL server
  ↓
Database

MySQL

TEXT
Django
  ↓
MySQL server
  ↓
Database

7. Understanding DATABASES

Let's break down:

PYTHON
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
    }
}

"default"

PYTHON
"default"

is the name of the database connection.

It is the default database Django uses.

You can configure multiple databases later, but most applications start with:

PYTHON
"default"

8. ENGINE

PYTHON
"ENGINE": "django.db.backends.sqlite3"

This tells Django which database backend to use.

Examples:

SQLite

PYTHON
"ENGINE": "django.db.backends.sqlite3"

PostgreSQL

PYTHON
"ENGINE": "django.db.backends.postgresql"

MySQL

PYTHON
"ENGINE": "django.db.backends.mysql"

9. NAME

For SQLite:

PYTHON
"NAME": BASE_DIR / "db.sqlite3"

means:

Use the db.sqlite3 file as the database.

For server-based databases, NAME usually means the database name, not a file path.

For example:

PYTHON
"NAME": "college_db"

10. PostgreSQL Configuration

A typical PostgreSQL configuration looks conceptually like:

PYTHON
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "college_db",
        "USER": "postgres",
        "PASSWORD": "your_password",
        "HOST": "localhost",
        "PORT": "5432",
    }
}

Let's understand each part.

11. PostgreSQL NAME

PYTHON
"NAME": "college_db"

This is the PostgreSQL database name.

12. PostgreSQL USER

PYTHON
"USER": "postgres"

This specifies the database user Django uses to connect.

13. PostgreSQL PASSWORD

PYTHON
"PASSWORD": "your_password"

This is the database user's password.

Important:

Don't commit real passwords to Git.

We'll discuss better configuration practices shortly.

14. PostgreSQL HOST

PYTHON
"HOST": "localhost"

This specifies where the database server is running.

For a database running on your own computer:

TEXT
localhost

or sometimes:

TEXT
127.0.0.1

15. PostgreSQL PORT

PYTHON
"PORT": "5432"

This is the port used by PostgreSQL in a typical installation.

Different database servers use different ports/configurations.

16. MySQL Configuration

A typical configuration:

PYTHON
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.mysql",
        "NAME": "college_db",
        "USER": "root",
        "PASSWORD": "your_password",
        "HOST": "localhost",
        "PORT": "3306",
    }
}

Typical MySQL port:

TEXT
3306

17. Database Configuration Comparison

Setting SQLite PostgreSQL MySQL
ENGINE sqlite3 postgresql mysql

USER Usually unnecessary Required Required
PASSWORD Usually unnecessary Required Required
HOST Usually unnecessary Often localhost/server Often localhost/server
PORT Usually unnecessary 5432 commonly 3306 commonly

18. Do You Need to Change models.py?

Usually, no.

This:

PYTHON
class Student(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField()

doesn't need to be rewritten just because you change:

TEXT
SQLite → PostgreSQL

The ORM abstracts much of the database-specific SQL.

19. But You Need the Correct Driver

Django needs a database adapter/driver to communicate with certain database systems.

For PostgreSQL, you generally install a PostgreSQL Python driver.

For MySQL, you generally install a compatible MySQL driver.

The exact package choice can depend on your Django/Python environment and deployment setup.

Conceptually:

TEXT
Django
  ↓
Python database driver
  ↓
Database server

20. Why Is a Driver Needed?

Django's Python code cannot directly communicate with every database protocol by itself.

The driver acts as the bridge.

TEXT
Django ORM
    ↓
Database Driver
    ↓
PostgreSQL / MySQL

21. Migrations and Database Configuration

Remember Module 27:

BASH
python manage.py makemigrations

creates migration files.

Then:

BASH
python manage.py migrate

applies those migrations to the configured database.

So:

TEXT
models.py
   ↓
makemigrations
   ↓
migration files
   ↓
migrate
   ↓
DATABASES["default"]
   ↓
Database

22. Very Important Distinction

makemigrations

Creates migration files.

BASH
python manage.py makemigrations

migrate

Actually applies migrations to the configured database.

BASH
python manage.py migrate

Therefore:

Changing the model and running makemigrations alone does not update the database schema.

23. What Happens When You Run migrate?

Suppose you have:

PYTHON
class Student(models.Model):
    name = models.CharField(max_length=100)

You run:

BASH
python manage.py makemigrations

Django generates something like:

TEXT
0001_initial.py

Then:

BASH
python manage.py migrate

Django translates the migration operations into database-specific SQL and applies them.

Conceptually:

TEXT
Migration
   ↓
Database-specific SQL
   ↓
Database schema

24. Does Django Always Generate the Same SQL?

No.

Different databases have different SQL dialects and capabilities.

Django's database backend translates ORM operations/migrations appropriately.

That's one of the major benefits of using the ORM.

25. Checking Database Connection

A useful command is:

BASH
python manage.py check

This checks for many Django project configuration issues.

It isn't a universal database connectivity test, but it can identify configuration problems.

Running:

BASH
python manage.py migrate

also requires Django to communicate with the configured database, so connection problems often appear there.

26. Common Database Error

You may see something like:

TEXT
OperationalError

This is a broad database-operation error.

Possible causes include:

  • Database server isn't running
  • Wrong database name
  • Wrong username
  • Wrong password
  • Wrong host
  • Wrong port
  • Missing database driver
  • Database doesn't exist
  • Permission problem
  • Network issue

27. MySQL/PostgreSQL Server Must Be Running

SQLite doesn't normally require you to start a separate database server.

But PostgreSQL and MySQL generally use database server processes.

Conceptually:

TEXT
SQLite:
Django → File

PostgreSQL:
Django → PostgreSQL Server

MySQL:
Django → MySQL Server

If the PostgreSQL/MySQL server isn't running, Django may not be able to connect.

28. Environment Variables

This is an important real-world concept.

Instead of writing:

PYTHON
PASSWORD = "my_real_password"

directly into source code, applications commonly use environment variables or a secrets-management mechanism.

Conceptually:

TEXT
Environment
    ↓
DB_PASSWORD
    ↓
settings.py
    ↓
DATABASES

29. Example With Environment Variables

Conceptually:

PYTHON
import os

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ.get("DB_NAME"),
        "USER": os.environ.get("DB_USER"),
        "PASSWORD": os.environ.get("DB_PASSWORD"),
        "HOST": os.environ.get("DB_HOST"),
        "PORT": os.environ.get("DB_PORT"),
    }
}

Now credentials don't have to be hard-coded directly into the Python source.

30. Why Environment Variables?

Imagine you push your project to GitHub.

If you have:

PYTHON
"PASSWORD": "MyRealPassword123"

you may accidentally expose your database credentials.

Instead:

PYTHON
"PASSWORD": os.environ.get("DB_PASSWORD")

allows the environment to supply the secret.

31. Development vs Production

For learning:

TEXT
SQLite

is extremely convenient.

For production, depending on the application, a server-based relational database such as PostgreSQL is often a strong choice.

But there is no universal rule that every production Django project must use PostgreSQL.

The appropriate database depends on:

  • Application requirements
  • Scale
  • Deployment environment
  • Existing infrastructure
  • Team expertise
  • Database features required

32. Multiple Databases

Django can support more than one database.

For example:

PYTHON
DATABASES = {
    "default": {
        ...
    },
    "analytics": {
        ...
    },
}

Then Django can route particular operations to different databases.

This is an advanced topic.

For your syllabus, understand the concept:

Django can be configured with multiple database connections.

33. Database Router

When using multiple databases, Django can use database routers to determine:

Which database should handle this model/query/migration operation?

Conceptually:

TEXT
Student
   ↓
Router
   ↓
Database A

Analytics
   ↓
Router
   ↓
Database B

You generally won't need to write a router unless you're actually using multiple databases.

34. using()

You can explicitly choose a database for a QuerySet:

PYTHON
Student.objects.using("analytics").all()

Conceptually:

Execute this QuerySet against the database connection named analytics.

36. db.sqlite3

When using SQLite, you'll commonly see:

TEXT
db.sqlite3

after migrations have been applied.

For example:

TEXT
College/
├── manage.py
├── db.sqlite3
├── College/
└── students/

This file contains the SQLite database.

37. Can You Delete db.sqlite3?

During development, sometimes developers delete and recreate a local SQLite database when intentionally resetting a disposable project.

But don't treat this as a normal production database reset.

Deleting it means:

You are deleting the database file and therefore the data stored in it.

If migrations remain, you can often create a fresh database by running:

BASH
python manage.py migrate

But this does not recover the old data.

38. Database Backup vs Migration

Another important distinction:

Migration

Describes database schema changes.

TEXT
models changed
   ↓
migration

Backup

Preserves actual database data.

TEXT
Database
   ↓
Backup

Therefore:

Migrations are not backups.

39. ORM Hides Much of the Database Difference

Suppose:

PYTHON
Student.objects.filter(
    marks__gte=80
)

You generally don't write different ORM code for:

TEXT
SQLite
PostgreSQL
MySQL

The Django database backend handles the database-specific details.

That's one of the major benefits of Django ORM.

40. But ORM Is Not Magic

Different databases can have:

  • Different supported features
  • Different SQL behavior
  • Different performance characteristics
  • Different indexing capabilities
  • Different configuration requirements

So switching databases isn't always completely effortless for every project.

For basic Django CRUD, however, the ORM gives you a high level of portability.

41. Database Indexes

An index is a database structure that can speed up certain queries.

Suppose you frequently search:

PYTHON
Student.objects.filter(
    email="aman@gmail.com"
)

You may consider indexing the relevant field.

For example:

PYTHON
email = models.EmailField(
    db_index=True
)

This tells Django to create a database index for that field through migrations.

42. Why Indexes Matter

Without a suitable index, the database may need to inspect many rows.

Conceptually:

TEXT
1,000,000 rows
      ↓
Search
      ↓
Potentially inspect many rows

With an appropriate index:

TEXT
Index
  ↓
Locate matching rows faster

But indexes also have costs:

  • Additional storage
  • More work during inserts/updates/deletes

Therefore:

Don't index every field blindly.

43. Unique Fields and Indexing

Consider:

PYTHON
email = models.EmailField(
    unique=True
)

A uniqueness constraint generally requires the database to enforce uniqueness and is commonly backed by an index/unique structure depending on the database.

This is one reason constraints are useful not just for application validation but for database integrity.

44. Database Connection Error Example

Suppose PostgreSQL configuration says:

PYTHON
"HOST": "localhost",
"PORT": "5432",

but PostgreSQL isn't running.

You might receive an error similar to:

TEXT
could not connect to server

Debug systematically:

TEXT
1. Is PostgreSQL installed?
2. Is the server running?
3. Is the database name correct?
4. Is the username correct?
5. Is the password correct?
6. Is the host correct?
7. Is the port correct?
8. Is the Python driver installed?
9. Does the user have permission?

45. Database Configuration Error Example

Suppose Django says:

TEXT
ModuleNotFoundError

related to the database backend/driver.

This may mean:

The required Python database driver isn't installed or isn't available in the current virtual environment.

First check that you're using the correct virtual environment.

Then install the appropriate driver according to your database/Django setup.

53. Important Viva Questions

Q1. Where is Django's database configuration stored?

In the DATABASES setting in settings.py.

Q2. What is the default Django database?

SQLite.

Q3. What is the default SQLite database file commonly called?

db.sqlite3.

Q4. What does ENGINE specify?

It specifies the Django database backend used to communicate with the database.

Q5. What does NAME mean?

It identifies the database. For SQLite it is typically the database file path; for server-based databases it generally identifies the database name.

Q6. What is a database driver?

A database driver is software that allows Django/Python to communicate with a particular database system.

Q7. Why use environment variables for database credentials?

To avoid hard-coding sensitive credentials in source code and make configuration safer and easier across environments.

Q8. Can Django use multiple databases?

Yes. Django supports configuring multiple database connections.

Q9. What is the difference between a migration and a database backup?

A migration describes/applies schema changes, while a backup preserves database data for recovery.

Q10. Does makemigrations modify the database?

No. It creates migration files based on model changes.

Q11. Does migrate modify the database?

Yes. It applies migrations to the configured database.

Q12. What is select_related() related to?

It optimizes fetching single-valued relationships such as ForeignKey and OneToOne.

54. Important Interview Question

"If I change from SQLite to PostgreSQL, do I have to rewrite all my ORM queries?"

A good answer:

"Usually no. Django's ORM abstracts much of the database-specific SQL, so normal model and QuerySet code can remain largely the same. However, database-specific features, constraints, behavior, performance, and configuration can require changes."

That's a strong interview answer.
