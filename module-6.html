Module 6 — Your First Django View

Now we are entering the core of Django.

You already know:

TEXT
Project
   ↓
App
   ↓
views.py

Now we'll connect everything:

TEXT
Browser
   ↓
URL
   ↓
View
   ↓
Response
   ↓
Browser

By the end of this module, you should be able to independently write a basic Django view and understand exactly what happens when the browser requests a page.

1. What is a View?

A view is the part of a Django application that receives an HTTP request and returns an HTTP response.

In simple words:

View = code that decides what response the user should receive.

For example, if a user visits:

TEXT
/about/

Django can call an about view, which might return:

TEXT
Welcome to About Page

2. Where Do We Write Views?

For an app called:

TEXT
students

the views normally go in:

TEXT
students/views.py

Initially Django generates something similar to:

PYTHON
from django.shortcuts import render

# Create your views here.

We'll modify this file.

3. Your First View

Replace/add the following:

PYTHON
from django.http import HttpResponse

def home(request):
    return HttpResponse("Hello World")

That's a complete basic Django view.

Let's understand every part.

4. Importing HttpResponse

PYTHON
from django.http import HttpResponse

We're importing HttpResponse from:

TEXT
django.http

HttpResponse allows us to send a response back to the browser.

5. Creating the View Function

PYTHON
def home(request):

This is a normal Python function.

The function name is:

TEXT
home

The parameter:

TEXT
request

represents the incoming HTTP request.

6. Why Does the View Have request?

When Django calls your view, it passes an HttpRequest object containing information about the incoming request.

Conceptually:

TEXT
Browser
   |
   | Request
   ↓
Django
   |
   | request object
   ↓
home(request)

The request can contain information such as:

  • HTTP method
  • URL/path
  • GET parameters
  • POST data
  • cookies
  • authenticated user
  • headers

We'll explore these in Unit II and Unit VI.

7. Returning a Response

Our code:

PYTHON
return HttpResponse("Hello World")

creates an HTTP response.

So:

TEXT
home(request)
      ↓
HttpResponse("Hello World")
      ↓
Browser

8. Is request a String?

No.

This is important.

request is an object representing the HTTP request.

For example:

PYTHON
def home(request):
    print(request.method)
    return HttpResponse("Hello")

If the browser makes a GET request, this could print:

TEXT
GET

We'll learn more about this later.

9. Now We Have a Problem

We created:

PYTHON
def home(request):
    return HttpResponse("Hello World")

But if you open:

TEXT
/students/

Django doesn't automatically know that /students/ should call home().

We need URL routing.

This is the next important concept.

10. URL Routing

URL routing means:

Connecting a URL pattern to a view.

Conceptually:

TEXT
/students/
     ↓
home()

Django's URL system performs this mapping.

11. Create urls.py Inside the App

Django does not automatically create urls.py when using startapp.

So create:

TEXT
students/
│
├── urls.py
├── views.py
├── models.py
└── ...

Now our app has its own URL configuration.

12. Write the App's urls.py

Inside:

TEXT
students/urls.py

write:

PYTHON
from django.urls import path
from . import views

urlpatterns = [
    path('', views.home),
]

Don't worry if this looks confusing.

We'll break it down.

13. from django.urls import path

PYTHON
from django.urls import path

We're importing Django's path() function.

path() is used to define URL patterns.

14. from . import views

PYTHON
from . import views

The . means:

Current package/app.

So this means:

Import the views module from the current app.

Our structure is:

TEXT
students/
├── urls.py
└── views.py

Therefore:

PYTHON
from . import views

imports:

TEXT
students/views.py

15. urlpatterns

Now:

PYTHON
urlpatterns = [
]

Django expects URL patterns to be placed in urlpatterns.

This is a special convention used by Django's URL dispatcher.

16. Our First URL Pattern

We write:

PYTHON
path('', views.home)

This means:

When this URL configuration receives the empty path, call views.home.

The empty string:

TEXT
''

represents the root of the URL configuration being included.

17. But How Does Django Reach students/urls.py?

Excellent question.

Currently Django primarily knows about:

TEXT
College/urls.py

It doesn't automatically know that:

TEXT
students/urls.py

exists.

So we need to connect the app URLs to the project URLs.

18. Open Project urls.py

Open:

TEXT
College/urls.py

You'll initially have something similar to:

PYTHON
from django.contrib import admin
from django.urls import path

urlpatterns = [
    path('admin/', admin.site.urls),
]

We'll modify it.

19. Import include

Change:

PYTHON
from django.urls import path

to:

PYTHON
from django.urls import path, include

Now we can use:

TEXT
include()

20. Connect the App

Change urlpatterns to:

PYTHON
urlpatterns = [
    path('admin/', admin.site.urls),
    path('students/', include('students.urls')),
]

Now we have:

TEXT
students/
     ↓
students.urls
     ↓
views.home

21. Complete Code

Let's see all three files.

students/views.py

PYTHON
from django.http import HttpResponse

def home(request):
    return HttpResponse("Hello World")

students/urls.py

PYTHON
from django.urls import path
from . import views

urlpatterns = [
    path('', views.home),
]

College/urls.py

PYTHON
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('students/', include('students.urls')),
]

22. Now Run the Server

From the directory containing manage.py:

BASH
python manage.py runserver

Open:

TEXT
http://127.0.0.1:8000/students/

You should see:

TEXT
Hello World

🎉 You have just created your first URL → View → Response Django application.

23. Understand the Entire Flow

This is VERY IMPORTANT.

You visit:

TEXT
http://127.0.0.1:8000/students/

Step 1 — Browser

Browser sends:

TEXT
GET /students/

Step 2 — Project urls.py

Django finds:

PYTHON
path('students/', include('students.urls'))

So Django says:

/students/ belongs to students.urls.

Step 3 — App urls.py

Django enters:

TEXT
students/urls.py

and sees:

PYTHON
path('', views.home)

The remaining path is empty:

TEXT
''

So Django calls:

PYTHON
views.home(request)

Step 4 — View

The view executes:

PYTHON
return HttpResponse("Hello World")

Step 5 — Browser

Django sends the HTTP response back.

Browser displays:

TEXT
Hello World

24. Complete Diagram

Memorize the concept, not just the code:

TEXT
Browser
   |
   | GET /students/
   ↓
College/urls.py
   |
   | students/
   ↓
students/urls.py
   |
   | ''
   ↓
views.home(request)
   |
   ↓
HttpResponse("Hello World")
   |
   ↓
Browser

This is the foundation of Django URL routing.

25. Why Do We Use include()?

Suppose we have many apps:

TEXT
students
teachers
courses
accounts

Instead of putting every URL in:

TEXT
College/urls.py

we can organize them:

TEXT
College/urls.py
     |
     +-- students/urls.py
     |
     +-- teachers/urls.py
     |
     +-- courses/urls.py
     |
     +-- accounts/urls.py

This keeps the project organized.

26. Why Is include() Better?

Imagine 100 URLs.

Without app-level organization:

PYTHON
urlpatterns = [
    path('students/', ...),
    path('students/add/', ...),
    path('students/delete/', ...),
    path('teachers/', ...),
    path('teachers/add/', ...),
    path('courses/', ...),
    ...
]

The project URL file becomes huge.

With include():

PYTHON
urlpatterns = [
    path('students/', include('students.urls')),
    path('teachers/', include('teachers.urls')),
    path('courses/', include('courses.urls')),
]

Each app manages its own URLs.

27. URL Prefix Concept

Consider:

PYTHON
path('students/', include('students.urls'))

and inside students/urls.py:

PYTHON
path('', views.home)

The final URL is:

TEXT
/students/

If we instead write:

PYTHON
path('list/', views.home)

the final URL becomes:

TEXT
/students/list/

So Django effectively combines:

TEXT
students/
+
list/
=
students/list/

28. Another Example

Suppose:

Project URL

PYTHON
path('products/', include('products.urls'))

App URL

PYTHON
path('all/', views.all_products)

Then the final URL is:

TEXT
/products/all/

and it calls:

PYTHON
views.all_products

29. Does the URL Have to Match the Function Name?

No.

You can write:

PYTHON
path('', views.home)

The URL:

TEXT
/students/

calls:

TEXT
home()

The function name and URL don't have to be identical.

For example:

PYTHON
path('abc/', views.home)

would mean:

TEXT
/students/abc/

calls:

TEXT
home()

30. Multiple URLs

We can have:

PYTHON
urlpatterns = [
    path('', views.home),
    path('about/', views.about),
    path('contact/', views.contact),
]

Then:

TEXT
/students/          → home()
/students/about/    → about()
/students/contact/  → contact()

31. Multiple Views

Our views.py could contain:

PYTHON
from django.http import HttpResponse

def home(request):
    return HttpResponse("Home Page")

def about(request):
    return HttpResponse("About Page")

def contact(request):
    return HttpResponse("Contact Page")

And URLs:

PYTHON
from django.urls import path
from . import views

urlpatterns = [
    path('', views.home),
    path('about/', views.about),
    path('contact/', views.contact),
]

Now you have three pages.

32. Important: Why request Comes First

You'll generally see:

PYTHON
def home(request):

not:

PYTHON
def home():

Django passes the HTTP request object to the view.

So:

TEXT
Django
   ↓
home(request)

If you omit the required parameter:

PYTHON
def home():

Django will not be able to call it in the expected way.

33. Can We Name It Something Other Than request?

Technically, yes.

For example:

PYTHON
def home(req):
    return HttpResponse("Hello")

Python doesn't require the variable to be called request.

But conventionally, use:

PYTHON
request

because it clearly communicates what the object represents.

34. What is HttpResponse?

HttpResponse represents an HTTP response that Django can send back to the client.

Example:

PYTHON
return HttpResponse("Hello")

You can return HTML too:

PYTHON
return HttpResponse("<h1>Hello</h1>")

The browser can render the HTML.

However, in real Django applications, we'll generally use templates for HTML rather than putting large HTML strings inside views.

35. Common Mistake — Forgetting include

Suppose you write:

PYTHON
path('students/', include('students.urls'))

but don't import include:

PYTHON
from django.urls import path

You'll get an error because include isn't defined.

Correct:

PYTHON
from django.urls import path, include

36. Common Mistake — Wrong App URL

Suppose you have:

TEXT
students/urls.py

but write:

PYTHON
path('students/', include('student.urls'))

Notice:

TEXT
student

instead of:

TEXT
students

Django won't find the specified module.

The name must match your app/module structure.

37. Common Mistake — Wrong View Name

Suppose:

PYTHON
def home(request):

but URL says:

PYTHON
path('', views.home_page)

There is no:

TEXT
home_page

view.

So Django will produce an error.

The referenced view must exist.

38. Common Mistake — Missing Trailing Slash

Suppose:

PYTHON
path('about/', views.about)

The conventional URL is:

TEXT
/about/

Django's handling of missing trailing slashes can depend on configuration, especially APPEND_SLASH and middleware, but don't rely on automatic behavior in exam code.

For now, write the URL exactly as defined.

39. Viva Questions

Q1. What is a view?

A view is a function or class that receives a request and returns a response.

Q2. Where are function-based views generally written?

In the app's views.py file.

Q3. What is HttpResponse?

HttpResponse is a Django class used to construct an HTTP response that can be returned to the client.

Q4. Why does a view accept request?

Django passes the incoming HTTP request object to the view so the view can access information about the request.

Q5. What is urlpatterns?

urlpatterns is the list containing URL patterns that Django's URL dispatcher uses for routing requests.

Q6. What is path()?

path() is a Django function used to define URL patterns.

Q7. What is include()?

include() allows one URL configuration to include URL patterns from another URL configuration, commonly an app's urls.py.

Q8. Why do we use app-level urls.py?

It helps organize URL patterns by application and keeps the project URL configuration maintainable.

40. Viva Trap Question ⚠️

Teacher:

"Does views.py automatically connect a function to a URL?"

Answer:

No. Defining a view only creates the request-handling logic. We must map a URL pattern to that view using Django's URL configuration.

Excellent distinction.

41. Viva Trap Question

Teacher:

"Can a view return something other than HttpResponse?"

Yes.

A view can return an appropriate HTTP response, including responses produced by helpers such as:

PYTHON
render()

or:

PYTHON
redirect()

and other response types.

We'll learn render() in the Templates section and redirect() when we study forms/POST handling.
